## 1. 阶段目标

完成本阶段后，应能从一条 SQL 一直讲到存储和恢复：

```text
连接与解析
  -> 优化器生成执行计划
  -> InnoDB 访问 Buffer Pool 和数据页
  -> 修改内存页并记录 Redo / Undo
  -> Server 层写 Binlog
  -> 提交并在崩溃后恢复
```

## 2. InnoDB 与 MyISAM

现代业务表通常使用 InnoDB。

| 能力 | InnoDB | MyISAM |
|---|---|---|
| 事务 | 支持 | 不支持完整事务 |
| 行级锁 | 支持 | 主要是表级锁 |
| MVCC | 支持 | 不支持 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | Redo Log 等机制 | 能力较弱 |
| 聚簇索引 | 主键叶子保存完整行 | 数据与索引组织方式不同 |

面试中不要只背表格，应说出选择 InnoDB 的核心理由：事务、并发控制、崩溃恢复以及成熟的线上能力。

## 3. MySQL 分层

可以简化为两层：

```text
Server 层
  连接管理、权限、解析、预处理、优化器、执行器、Binlog

存储引擎层
  InnoDB 数据页、索引、Buffer Pool、事务、锁、Redo、Undo
```

一条查询大致经过：

```text
客户端建立连接
  -> 解析 SQL 并检查语义
  -> 优化器选择访问路径和连接顺序
  -> 执行器调用 InnoDB 接口读取记录
  -> 返回结果
```

MySQL 8 已移除旧版查询缓存，面试中不要继续把 Query Cache 作为现代查询主流程的一部分。

## 4. 数据页

InnoDB 以页为基本管理和 I/O 单位，常见默认页大小为 16KB。索引页、数据页并不是每查询一行就只读取几个字节，而是按页加载和缓存。

这能解释：

- B+Tree 为什么强调树高和页访问次数。
- 顺序访问为什么通常比大量随机回表更友好。
- 为什么窄索引可以在一个页中容纳更多键。
- 为什么随机主键插入可能造成页分裂和碎片。

具体页大小可以配置，回答时不应把 16KB 说成永远不可改变。

## 5. Buffer Pool

Buffer Pool 是 InnoDB 的核心内存缓存，用来缓存数据页、索引页以及相关管理信息。

### 5.1 查询一行数据

```text
通过索引定位目标页
  -> 检查目标页是否已在 Buffer Pool
  -> 命中则直接在内存中读取
  -> 未命中则从磁盘加载页到 Buffer Pool
  -> 根据事务可见性和查询条件返回记录
```

因此同一条 SQL 第一次和后续执行的耗时可能不同。不能仅凭一次本地执行判断 SQL 性能。

### 5.2 修改一行数据

可以粗略理解为：

```text
定位并加载数据页
  -> 在 Buffer Pool 中修改页
  -> 记录 Undo 信息
  -> 生成 Redo Log
  -> 数据页变成脏页
  -> 事务按提交协议完成
  -> 后台线程以后将脏页刷回数据文件
```

提交事务通常不需要同步把所有修改后的完整数据页立刻写回磁盘。WAL 和 Redo Log 使提交路径能够主要顺序写日志，并在崩溃后重做修改。

### 5.3 脏页

Buffer Pool 中已修改但尚未写回数据文件的页称为脏页。后台刷脏太慢可能导致：

- 脏页比例升高。
- Redo 空间压力。
- 前台查询被迫参与刷页。
- 延迟抖动。

排查时要结合磁盘 I/O、Buffer Pool 命中率、脏页比例、Redo 生成速率和检查点推进情况。

## 6. Change Buffer

对于符合条件且不在 Buffer Pool 中的二级索引页修改，InnoDB 可以先缓存变更，等索引页以后被读入时再合并，以减少随机 I/O。

理解边界：

- 主要针对二级索引页的部分修改场景。
- 唯一索引通常需要立即读取目标页检查唯一性，不能简单按相同方式延迟处理。
- 读多写少、修改后马上查询的场景，收益可能有限。
- 不要把 Change Buffer 与 Buffer Pool 混为一谈；前者缓存的是某些变更信息，后者缓存数据页和索引页。

## 7. Doublewrite Buffer

数据库写一个数据页时，如果操作系统或机器在写到一半时崩溃，可能产生部分页写入：磁盘上的页既不是旧页，也不是完整新页。

Redo Log 擅长重放逻辑或物理变更，但前提是基础页本身可识别。Doublewrite 机制会先把页写入一块可恢复区域，再写到最终数据文件位置。恢复时若发现最终页损坏，可以先取得完整页副本，再应用 Redo。

可以记住：

```text
Redo 解决“已提交修改如何重放”
Doublewrite 解决“数据页只写了一半”
```

## 8. Undo Log

Undo Log 保存修改前的信息或用于构造旧版本的信息，主要作用：

1. 事务回滚。
2. MVCC 一致性读的历史版本链。

执行：

```sql
UPDATE accounts
SET balance = balance - 100
WHERE id = 1;
```

事务回滚时，需要根据 Undo 信息恢复修改前状态；其他事务进行快照读时，也可能沿 Undo 版本链读取对其可见的旧版本。

Undo 不会在事务一提交就立即全部消失。只要还有旧 Read View 需要相关版本，就不能清理。这也是长事务会阻碍版本清理的重要原因。

## 9. Redo Log

Redo Log 是 InnoDB 层的重做日志，核心作用是崩溃恢复和持久性。

### 9.1 WAL

WAL 是 Write-Ahead Logging，即先写日志，再在以后将脏页写回数据文件。

```text
修改 Buffer Pool 中的数据页
  -> 生成 Redo 记录
  -> 提交时按策略持久化 Redo
  -> 后台异步刷脏页
```

日志通常比随机写大量数据页更连续、更紧凑，因此能够缩短事务提交路径。

### 9.2 Redo 是否记录完整 SQL？

不是。Redo 是 InnoDB 存储引擎层用于恢复页修改的信息，与 Server 层记录逻辑变更的 Binlog 不是同一层次。

### 9.3 Redo Buffer 与刷盘

事务产生的 Redo 会先进入内存缓冲，再按配置和时机写入日志文件并刷盘。`innodb_flush_log_at_trx_commit` 影响提交时的写入与刷盘策略。

面试回答配置时要强调：

- 更强的持久性通常需要更频繁 `fsync`。
- 放宽策略可能提高吞吐，但机器或操作系统崩溃时可能丢失最近事务。
- 具体选择应结合业务可接受的数据丢失窗口和基础设施能力。

## 10. Binlog

Binlog 属于 MySQL Server 层，记录数据库变更，主要用于：

- 主从复制。
- 按时间点恢复。
- 数据订阅和变更捕获。
- 审计或下游数据同步。

常见格式：

| 格式 | 特点 |
|---|---|
| Statement | 记录 SQL，体积可能较小，但某些非确定性语句存在一致性风险 |
| Row | 记录行变化，复制更可靠，日志量可能更大 |
| Mixed | 根据语句选择 Statement 或 Row |

生产中常见 Row 模式，但应根据真实环境回答。

`sync_binlog` 控制 Binlog 刷盘策略。数据库持久性不能只看一个参数，要同时考虑 Redo 和 Binlog 的提交与刷盘配置。

## 11. 三类日志对比

| 日志 | 所属层 | 主要作用 | 典型关键词 |
|---|---|---|---|
| Undo Log | InnoDB | 回滚、MVCC | 修改前版本、版本链 |
| Redo Log | InnoDB | 崩溃恢复、持久性 | WAL、重做页修改 |
| Binlog | Server | 复制、恢复、订阅 | 逻辑变更、全库归档 |

面试高频回答：

> Undo 解决回滚和历史版本，Redo 解决 InnoDB 崩溃恢复，Binlog 服务复制和数据恢复。Redo 与 Binlog 所属层、记录内容和用途都不同，不能互相简单替代。

## 12. 为什么需要两阶段提交

一个事务既要写 InnoDB 的 Redo，又要写 Server 层 Binlog。如果两者独立提交，中间发生崩溃，可能出现：

- Redo 有记录、Binlog 没有：主库恢复后有这次修改，但从库或按 Binlog 恢复时缺失。
- Binlog 有记录、Redo 未提交：从库或恢复系统认为修改存在，但主库自身没有提交。

因此事务提交主线可以简化为：

```text
写 Redo，并进入 prepare 状态
  -> 写 Binlog
  -> 将 Redo 标记为 commit
```

崩溃恢复时会结合 Redo 状态和 Binlog 中是否存在对应事务来决定提交还是回滚，从而保持两个日志一致。

### 12.1 崩溃点分析

#### Redo prepare 之前崩溃

事务没有完成 prepare，按未提交处理。

#### Redo prepare 后、Binlog 完整写入前崩溃

如果没有完整、有效的对应 Binlog，事务按未提交处理。

#### Binlog 完整写入后、Redo commit 前崩溃

恢复时可根据完整 Binlog 和事务标识确认事务应提交。

回答时不必陷入源码字段细节，但要说清目标：保证主库恢复结果与复制、Binlog 恢复结果一致。

## 13. 一条 UPDATE 的完整主线

执行：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 100 AND stock > 0;
```

可以这样回答：

```text
1. Server 层解析并优化 SQL。
2. 执行器调用 InnoDB，通过主键定位记录。
3. InnoDB 进行当前读并获取必要的行锁。
4. 记录 Undo 信息，用于回滚和版本链。
5. 修改 Buffer Pool 中的数据页，生成 Redo，数据页成为脏页。
6. Server 层生成 Binlog。
7. 通过两阶段提交协调 Redo 和 Binlog。
8. 提交后释放锁；脏页以后由后台线程刷入数据文件。
9. 若崩溃，InnoDB 使用 Redo 等信息恢复已提交修改。
```

这是面试模型，不代表所有内部动作严格按一句一动作串行发生。深入追问时再讨论组提交、日志缓冲和刷盘策略。

## 14. 主从复制基本流程

可以简化为：

```text
主库提交事务并生成 Binlog
  -> 从库拉取 Binlog
  -> 保存为中继日志
  -> 从库回放事务
  -> 数据逐渐追上主库
```

复制通常是异步或半同步语义，主库提交完成不等于所有从库已经应用完成，因此读写分离可能出现“刚写完马上读从库却读不到”的情况。

## 15. 高频追问

### 15.1 Redo 为什么提高写性能？

因为事务提交路径不必同步将所有随机分布的脏页写回各自数据文件，可以先持久化更连续的 Redo，再由后台批量刷脏。但 Redo 的首要目的仍是崩溃恢复，不能只回答“提高性能”。

### 15.2 数据已经有 Redo，为什么还需要 Binlog？

Redo 是 InnoDB 内部恢复日志，服务页级恢复并具有存储引擎属性；Binlog 是 Server 层的变更日志，可跨引擎服务复制、时间点恢复和数据订阅。两者职责不同。

### 15.3 提交成功后数据页还没落盘，会丢数据吗？

在正确的持久化配置下，已提交事务的 Redo 已经可靠持久化。崩溃后可以通过 Redo 重放到数据页，因此不要求提交瞬间就把所有脏页写回最终位置。

### 15.4 Buffer Pool 越大越好吗？

在专用数据库服务器上通常希望给 InnoDB 充分内存，但必须为操作系统、连接、排序、临时表、其他进程和突发开销保留空间。过大可能导致交换、OOM 或系统不稳定，应结合工作集和监控调整。
