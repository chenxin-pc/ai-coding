## 1. 阶段目标

场景题重点考察证据链，而不是背诵“加索引、分库分表”。稳定的回答方式是：

```text
确认现象
  -> 定位 SQL 或资源瓶颈
  -> 查看执行计划与运行指标
  -> 找到根因
  -> 选择低风险方案
  -> 压测、灰度、上线观察
```

## 2. 慢 SQL 排查流程

### 2.1 确认问题边界

先回答：

- 是所有 SQL 慢，还是一条接口中的特定 SQL 慢？
- 是一直慢，还是某个时间段偶发？
- 所有实例都慢，还是单个主库或从库慢？
- QPS、数据量、参数分布、发布和流量是否发生变化？
- 慢在数据库执行、连接池等待、网络，还是应用处理？

### 2.2 收集证据

常用证据：

- 慢查询日志和性能监控。
- SQL 的真实参数与调用频率。
- `EXPLAIN`、必要时谨慎使用 `EXPLAIN ANALYZE`。
- 扫描行数、返回行数、执行时间、锁等待时间。
- CPU、磁盘 I/O、Buffer Pool、连接数、临时表等指标。
- 当时是否有长事务、DDL、大批量任务或主从延迟。

### 2.3 分析执行计划

重点检查：

1. 是否选用了合适索引。
2. 估算和实际扫描行数是否过大。
3. 是否发生大量回表。
4. 连接顺序和连接列索引是否合理。
5. 是否出现代价较高的排序或临时表。
6. 条件是否存在函数、隐式转换、前置模糊匹配。
7. 统计信息是否过旧或数据严重倾斜。

### 2.4 验证优化

不能只证明新 SQL “能跑”。至少比较：

- 相同数据量和参数下的耗时。
- 扫描行数与返回行数。
- CPU、I/O、锁和临时空间。
- 高并发下的吞吐和 P95/P99。
- 新索引对写入和磁盘空间的影响。

面试回答：

> 我会先用监控和慢日志确认是哪类请求、哪条 SQL 以及真实参数，再看执行计划和实际扫描行数，判断索引、回表、连接、排序、锁等待或资源瓶颈。修改后用相同数据和流量压测，比较耗时与扫描量，再灰度上线并继续观察。

## 3. 为什么一条 SQL 偶尔很慢

偶发慢通常不能仅靠静态 `EXPLAIN` 解释。常见原因：

- 等待其他事务持有的行锁或元数据锁。
- Buffer Pool 未命中，需要磁盘读取。
- 脏页刷盘、Redo 空间或检查点压力。
- 同时发生大查询、备份、DDL 或批处理。
- 数据库 CPU、磁盘或连接数瞬时饱和。
- 查询参数不同导致扫描数据量差异巨大。
- 统计信息变化，优化器选择了不同执行计划。
- 主从延迟或从库正在回放大事务。
- 应用连接池等待或网络延迟被误认为 SQL 慢。

排查关键是拿到慢时刻的锁等待、资源指标、真实参数和执行统计，而不是用正常时刻的一次执行替代现场。

## 4. 深分页

```sql
SELECT id, user_id, status, create_time
FROM orders
ORDER BY id
LIMIT 1000000, 20;
```

数据库通常需要找到并跳过前 100 万行，才能返回后 20 行。偏移量越大，扫描和丢弃成本越高。

### 4.1 游标分页

如果按唯一递增键翻页：

```sql
SELECT id, user_id, status, create_time
FROM orders
WHERE id > ?
ORDER BY id
LIMIT 20;
```

优点：能直接从上次位置继续扫描，性能更稳定。

限制：

- 不适合任意跳到第 N 页。
- 排序键必须稳定。
- 非唯一排序字段需要加入唯一键作为游标，避免重复或漏数据。

例如按时间倒序：

```sql
SELECT id, user_id, status, create_time
FROM orders
WHERE (create_time, id) < (?, ?)
ORDER BY create_time DESC, id DESC
LIMIT 20;
```

对应索引可考虑：

```sql
KEY idx_time_id (create_time, id)
```

### 4.2 延迟关联

必须保留偏移分页时，可以先利用较窄的覆盖索引取得主键，再关联完整记录：

```sql
SELECT o.id, o.user_id, o.status, o.create_time
FROM orders o
JOIN (
    SELECT id
    FROM orders
    ORDER BY id
    LIMIT 1000000, 20
) x ON x.id = o.id
ORDER BY o.id;
```

它仍要跳过大量索引项，但可以减少扫描宽行和大量无效回表，是否有效必须实测。

## 5. ORDER BY 如何使用索引

联合索引可以为匹配的排序顺序提供有序结果，从而避免额外排序。

假设索引：

```sql
KEY idx_user_time (user_id, create_time, id)
```

查询：

```sql
SELECT id, create_time
FROM orders
WHERE user_id = 100
ORDER BY create_time, id
LIMIT 20;
```

`user_id` 等值确定一个连续范围，后续记录已按 `create_time, id` 排序，可能直接利用索引顺序。

常见无法完整利用索引排序的原因：

- 排序字段不符合联合索引顺序。
- 跳过左侧索引列。
- 多列升降序组合与索引方向不匹配。
- 前面存在无法固定的范围条件。
- 查询返回范围过大，优化器选择其他计划。

`Using filesort` 表示 MySQL 需要额外排序过程，不等于一定写磁盘。是否需要优化取决于数据量和实际耗时。

## 6. GROUP BY 与聚合优化

方向包括：

- 在 `WHERE` 阶段尽早过滤数据。
- 让过滤列和分组列形成合适的联合索引。
- 避免返回无用列。
- 大范围实时报表考虑汇总表、离线计算或分析型数据库。
- 检查分组是否产生大型内部临时表。

不要为了追求单条 SQL 而把所有复杂报表都压在在线交易库上。OLTP 和大规模 OLAP 的访问模式不同。

## 7. LIKE '%关键词%' 如何优化

B+Tree 可以较好支持前缀匹配：

```sql
WHERE title LIKE 'MySQL%';
```

任意位置匹配：

```sql
WHERE title LIKE '%MySQL%';
```

通常无法通过普通 B+Tree 直接确定连续范围。可选方案：

- 数据量很小或查询频率低时接受扫描。
- 根据业务改成前缀检索。
- 使用 MySQL 全文索引，并确认分词和语言需求。
- 使用 Elasticsearch 等专门搜索系统。
- 对固定格式字段拆分或建立可搜索的派生列。

选型时考虑一致性、延迟、运维成本和搜索语义，而不是一遇到模糊查询就必然引入新系统。

## 8. 批量插入

相比逐行多次往返，批量插入通常更高效：

```sql
INSERT INTO orders (id, user_id, amount)
VALUES
    (1, 100, 10.00),
    (2, 101, 20.00),
    (3, 102, 30.00);
```

优化方向：

- 合理批量，减少网络往返和事务提交次数。
- 使用显式事务，避免每行单独提交。
- 批次不要无限大，避免日志、锁、内存和复制压力。
- 按主键趋势顺序写入，降低随机页修改。
- 控制不必要索引数量。
- 导入任务与在线流量错峰，并监控复制延迟。

## 9. 大量数据删除

一次删除数百万行可能造成：

- 大事务和大量 Undo、Redo、Binlog。
- 锁持有时间长。
- 主从复制延迟。
- Buffer Pool 和磁盘 I/O 压力。
- 事务失败后的高额回滚成本。

常见方案：

```sql
DELETE FROM event_log
WHERE create_time < '2025-01-01'
ORDER BY id
LIMIT 5000;
```

由任务循环分批执行，并根据线上负载限速。删除条件要有合适索引，每批独立提交，并记录进度与失败重试状态。

如果数据天然按时间生命周期管理，可以评估分区表，通过删除分区快速淘汰整段数据。但分区不是万能优化，需要遵守分区键和唯一键等规则，并评估版本、运维和查询模式。

## 10. 大表添加索引

需要提前确认：

- 表大小和新增索引预计空间。
- MySQL 版本与具体 DDL 是否支持在线算法。
- 是否需要扫描全表和构建索引。
- 元数据锁对业务的影响。
- 额外磁盘、I/O、CPU、Redo/Binlog 和复制延迟。
- 是否存在长事务阻塞 DDL。
- 回滚方案和观察指标。

操作思路：

```text
在相同规模环境评估
  -> 检查磁盘和复制能力
  -> 清理或终止不合理长事务（按变更流程）
  -> 选择低峰和合适在线 DDL 方式
  -> 灰度或先在从库验证
  -> 持续观察锁、延迟和资源
```

不要把“Online DDL”理解为“完全没有锁、没有资源成本”。开始和结束阶段仍可能涉及元数据锁，构建过程也会消耗大量资源。

## 11. 防止库存超卖

### 11.1 条件更新

```sql
UPDATE products
SET stock = stock - 1
WHERE id = ?
  AND stock > 0;
```

应用检查受影响行数。数据库在同一条原子更新中完成检查和扣减，能避免两个请求先后读到同一库存后都成功写回的问题。

如果一次购买数量为 `n`：

```sql
UPDATE products
SET stock = stock - ?
WHERE id = ?
  AND stock >= ?;
```

### 11.2 悲观锁

```sql
START TRANSACTION;

SELECT stock
FROM products
WHERE id = ?
FOR UPDATE;

-- 检查库存并更新

COMMIT;
```

适合需要读取多个字段并执行复杂校验的场景，但事务必须短，条件必须有索引。

### 11.3 乐观锁

```sql
UPDATE products
SET stock = stock - 1,
    version = version + 1
WHERE id = ?
  AND version = ?
  AND stock > 0;
```

失败后根据业务进行有限重试。高冲突场景下大量失败重试可能降低性能。

### 11.4 还需要处理什么？

防超卖不等于完整库存系统，还要处理：

- 重复请求和幂等。
- 下单成功但支付失败后的库存释放。
- 超时订单关闭。
- 消息重复和最终一致性。
- 热点商品的限流、排队或库存分片。

## 12. 支付回调幂等

支付平台可能重复发送回调，系统不能重复入账或重复发货。

典型方案：

1. 使用支付流水号建立唯一索引。
2. 在事务中检查并更新订单状态。
3. 使用状态机限制合法状态转换。
4. 写业务记录与状态变更处于同一事务。
5. 重复回调返回成功，但不重复执行副作用。

```sql
UPDATE orders
SET status = 'PAID', paid_at = NOW()
WHERE id = ?
  AND status = 'UNPAID';
```

受影响行数为 1 表示本次完成状态转换；为 0 时要查询当前状态，区分已经处理、订单不存在或状态异常。

仅在应用层“先查是否处理过”而没有事务和唯一约束，仍可能在并发下重复执行。

## 13. 主从延迟与读写一致性

常见原因：

- 从库硬件或 I/O 能力较弱。
- 主库产生写入速度超过从库应用速度。
- 大事务、单线程瓶颈或热点冲突。
- 从库同时承担大量慢查询。
- 网络延迟或复制错误。

“写后立刻读”可采用：

- 关键链路在一定时间内读主库。
- 写操作返回必要结果，避免立即二次读取。
- 等待特定复制位点后再读取从库。
- 对强一致需求直接使用主库。
- 非关键查询接受短暂最终一致性。

不能用缓存简单掩盖所有复制延迟，因为缓存本身也存在更新顺序和一致性问题。

## 14. 分库分表追问

只有在单库容量、吞吐、维护窗口或业务隔离确实成为瓶颈时才考虑分库分表。它会引入：

- 跨分片查询、排序和分页。
- 分布式事务和一致性问题。
- 全局唯一 ID。
- 扩容与数据迁移。
- 路由键选择。
- 运维、监控和故障恢复复杂度。

全局 ID 可选数据库号段、Snowflake 类趋势递增 ID 等方案。选择时权衡趋势性、可用性、时钟依赖、长度和是否暴露业务信息。

回答场景题时先证明单库瓶颈，优先考虑 SQL、索引、表结构、缓存、读写分离和归档等较低复杂度方案，再讨论分片。
