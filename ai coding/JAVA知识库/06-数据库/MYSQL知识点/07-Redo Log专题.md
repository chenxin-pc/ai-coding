## 1. 一句话理解 Redo Log

Redo Log 是 InnoDB 存储引擎的重做日志，核心作用是保证事务持久性并支持崩溃恢复。

它采用“先记录页修改、以后再写数据页”的方式，使事务提交时不必同步把所有随机分布的数据页写回磁盘。

```text
先顺序写 Redo Log
        ->
以后异步写数据页
```

## 2. 为什么需要 Redo Log

InnoDB 修改数据时，通常先修改 Buffer Pool 中的数据页。若每个事务提交时都立即把所有完整数据页写回磁盘，会产生大量随机 I/O，提交延迟也会很高。

Redo Log 将提交路径转换为更紧凑、相对连续的日志写入：

```text
直接刷数据页
  多个随机位置、每页通常较大

写 Redo Log
  记录页修改、写入更连续
```

数据页可以由后台线程批量刷新；如果数据库在数据页刷新前宕机，可以利用已经持久化的 Redo 恢复修改。

## 3. 一次数据修改的基本过程

执行：

```sql
UPDATE account
SET balance = balance - 100
WHERE id = 1;
```

可以简化为：

```text
1. 定位并加载相关数据页到 Buffer Pool
2. 生成 Undo 信息
3. 修改 Buffer Pool 中的数据页
4. 生成 Redo，先写入 Redo Log Buffer
5. 数据页成为脏页
6. 事务按照提交协议完成 Commit 或 Rollback
7. 后台线程在合适的时机将脏页写回数据文件
```

Redo 记录的是 InnoDB 数据页层面的修改信息，可以理解为偏物理的页级变更。它不是原始 SQL，也不等同于一行数据修改前后的完整值。

## 4. WAL：日志先行

WAL 是 Write-Ahead Logging，即日志先行：

> 与脏页修改相关的 Redo 必须先满足写入和持久化要求，随后才允许对应脏页写入数据文件。

```text
修改 Buffer Pool 数据页
        ->
生成 Redo
        ->
Redo 先于对应脏页落盘
        ->
脏页写入数据文件
```

WAL 约束的是 Redo 与数据页的写入顺序，不是事务提交顺序。无论修改所属的事务是否已经提交，只要准备刷新对应脏页，就必须先保证有足够的 Redo 恢复依据。

如果反过来先写数据页、后写 Redo，中间发生宕机，磁盘上可能已经出现部分新修改，但日志中没有完整恢复依据，数据页就可能处于无法可靠恢复的状态。

## 5. Buffer Pool 能否存在未提交数据

可以。事务修改记录时，会直接修改 Buffer Pool 中的数据页，因此其中完全可能包含尚未提交的事务修改。

例如：

```sql
BEGIN;

UPDATE account
SET balance = 900
WHERE id = 1;

-- 尚未 COMMIT
```

此时可以概念化为：

```text
Buffer Pool 当前记录：balance = 900，事务尚未提交
Undo Log 历史版本： balance = 1000
```

InnoDB 不依靠“为每个事务复制一份数据页”实现隔离，而是通过锁、MVCC、事务状态和 Undo 版本链控制可见性。

在常用的 `READ COMMITTED` 和 `REPEATABLE READ` 隔离级别下：

- 当前事务可以看到自己的修改。
- 其他快照读会根据 Read View 和 Undo 版本链寻找可见的已提交版本。
- 其他事务修改同一行时，通常需要等待相关行锁。
- `READ UNCOMMITTED` 可能发生脏读。

脏页只表示内存页与数据文件中的页不一致，并不代表页内所有修改都已经提交。

## 6. 未提交事务的脏页能否写入磁盘

可以。InnoDB 允许事务提交前将包含未提交修改的脏页写入数据文件，也不要求事务提交时立即写回全部相关数据页。这可以概括为类似 `STEAL + NO-FORCE` 的策略：

- `STEAL`：未提交事务修改过的脏页可以提前写入数据文件。
- `NO-FORCE`：事务提交时不强制立即写回所有相关数据页。

一个页可能同时包含多个事务的修改：

```text
数据页 P
  T1 的修改：已提交
  T2 的修改：未提交
  T3 的修改：已提交
```

刷页时写的是整个页，不会只写其中已提交的部分。只要相关 Redo 先满足 WAL 要求，该页就可以写入数据文件。

如果 T2 后续回滚，InnoDB 使用 Undo 撤销它；如果数据库在此时宕机，恢复过程也会识别并回滚 T2。

因此：

```text
事务是否提交 != 脏页是否刷盘
```

## 7. Redo 持久化是否必须等到 Commit

不需要。Redo 在事务修改数据时就会生成，并先进入 Redo Log Buffer。`COMMIT` 是触发或确认 Redo 持久化的重要时机，但不是唯一时机。

以下情况都可能使未提交事务的 Redo 提前写入或持久化：

- 刷新相关脏页时需要满足 WAL。
- Redo Log Buffer 空间不足。
- 后台线程周期性刷新。
- 推进 Checkpoint。
- 其他事务提交触发 Group Commit，将连续 LSN 范围内的日志一起刷新。

例如：

```text
T1：生成 Redo，LSN = 100，尚未提交
T2：生成 Redo，LSN = 200，随后提交
```

T2 提交时若将日志推进到 LSN 200，位于前面的 T1 Redo 也可能一起持久化，但 T1 仍然没有提交。

必须区分三个事件：

| 事件 | 含义 |
|---|---|
| 生成 Redo | 内存数据页发生了修改 |
| Redo 持久化 | 修改已经具备崩溃恢复依据 |
| 事务 Commit | 修改在事务语义上正式生效 |

所以：

```text
Redo 已落盘 != 事务已提交
```

## 8. Write、Flush 与提交参数

Redo 从内存到稳定存储大致经过：

```text
Redo Log Buffer
  -> write 到操作系统文件缓存
  -> flush / fsync 到稳定存储
```

口语中的“写日志”和“落盘”容易混淆。讨论故障风险时，需要明确是仅进入操作系统缓存，还是已经通过 `fsync` 等机制写入稳定存储。

`innodb_flush_log_at_trx_commit` 控制提交时的日志写入和刷盘策略：

| 参数值 | 提交时的大致行为 | 特点 |
|---|---|---|
| `1` | 每次提交都写 Redo 并刷盘 | 持久性最强，常见默认值 |
| `2` | 每次提交写入操作系统缓存，通常周期性刷盘 | 机器或操作系统崩溃时可能丢失最近事务 |
| `0` | 通常由后台线程周期性写入并刷盘 | MySQL 进程或机器崩溃时都可能丢失最近事务 |

当值为 `1` 时，`COMMIT` 的核心保证是：

> 在向客户端返回提交成功前，确认该事务提交所需的 Redo 已经持久化。

这不代表 Redo 一定是在执行 `COMMIT` 的瞬间才第一次持久化，它可能已经提前落盘。

## 9. LSN 与 Checkpoint

LSN（Log Sequence Number）用于标识 Redo 的位置和修改顺序。它帮助 InnoDB 判断：

- 日志已经写到哪里。
- 日志已经持久化到哪里。
- 数据页包含了哪些修改。
- 崩溃恢复需要从哪里开始。
- 哪些旧日志空间可以复用。

数据页也记录相关 LSN。若某个脏页最新修改对应的 LSN 为 100，那么刷新该页之前，Redo 至少需要推进到满足 LSN 100 的 WAL 要求。

Redo 空间会循环复用。Checkpoint 表示某个位置之前的 Redo 所对应的数据页修改已经安全写入数据文件，因此旧日志空间可以复用：

```text
持续生成 Redo
  -> 后台刷新脏页
  -> 推进 Checkpoint
  -> 复用旧 Redo 空间
```

如果脏页刷新速度跟不上 Redo 生成速度，Checkpoint 难以前进，就可能出现强制刷脏、写入抖动甚至前台阻塞。

## 10. 崩溃恢复为什么会回放未提交事务

Redo Recovery 的首要目标是把数据页恢复到物理一致的状态，而不是先判断每条页修改所属的事务是否提交。

恢复过程可以从逻辑上理解为：

```text
第一阶段：Redo
恢复数据页，可能包括未提交事务的页修改
        ->
第二阶段：Undo
识别崩溃时未完成的事务，并撤销其修改
```

Redo 主要按照页和 LSN 组织，同一个页面上可能混合多个事务的修改：

```text
Redo LSN 100：T1 修改页 P1
Redo LSN 110：T2 修改页 P2
Redo LSN 120：T1 修改页 P3
Redo LSN 130：T3 修改页 P2
```

如果简单跳过某个未提交事务的 Redo，页分裂、索引结构调整等操作可能只恢复了一部分，破坏页面的物理一致性。因此通常先恢复页面，再处理事务一致性。

示例：

```text
崩溃前：
T1 修改 A，已经提交
T2 修改 B，尚未提交

恢复时：
1. Redo 可能先恢复 A 和 B
2. 判断 T1 已提交，保留 A
3. 判断 T2 未提交，使用 Undo 撤销 B
```

## 11. 如何识别已提交和未提交事务

InnoDB 不是仅靠 Redo 判断事务是否提交，而是结合事务系统、Rollback Segment 和 Undo Log 中的信息重建事务状态。

聚簇索引记录还包含用于版本追踪的隐藏字段：

```text
DB_TRX_ID    最后修改该记录的事务 ID
DB_ROLL_PTR  指向相关 Undo 记录
```

恢复时如果发现某个事务仍处于活跃、未完成状态，就沿其 Undo 记录逆序撤销修改；已经提交的事务则保留修改。

对于处于两阶段提交 `prepare` 状态的事务，还需要结合 Binlog 中是否存在对应事务来决定最终提交或回滚。

## 12. Redo、Undo 与 Binlog

| 日志 | 所属层 | 主要作用 | 内容特点 |
|---|---|---|---|
| Redo Log | InnoDB | 崩溃恢复、持久性 | 页级修改信息 |
| Undo Log | InnoDB | 事务回滚、MVCC | 修改前版本和版本链 |
| Binlog | MySQL Server | 复制、时间点恢复、订阅 | 逻辑变更事件 |

可以简单记忆：

```text
Redo：重做页面修改
Undo：撤销事务修改、构造历史版本
Binlog：记录数据库发生过的逻辑变更
```

Redo 与 Binlog 通过内部两阶段提交保持一致，主线可以简化为：

```text
写 Redo，进入 prepare
  -> 写 Binlog
  -> 完成事务提交
```

这样可以避免主库自身的崩溃恢复结果与 Binlog 复制、时间点恢复结果不一致。

## 13. 一条 UPDATE 的完整主线

执行：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 100 AND stock > 0;
```

完整主线可以概括为：

```text
1. Server 层解析并优化 SQL
2. 执行器调用 InnoDB 定位记录
3. InnoDB 获取必要的锁
4. 生成 Undo，用于回滚和 MVCC
5. 修改 Buffer Pool 中的数据页
6. 生成 Redo，数据页成为脏页
7. Server 层生成 Binlog
8. Redo 与 Binlog 通过两阶段提交协调
9. 提交后释放锁，脏页以后异步刷盘
10. 如果崩溃，先用 Redo 恢复页面，再用 Undo 撤销未完成事务
```

这是一条便于理解和面试表达的主线，不表示所有内部动作都严格按照一句一动作串行执行。

## 14. 高频问题

### 14.1 Redo 为什么能提高写性能？

事务提交时不必同步刷新所有随机分布的数据页，可以先持久化更紧凑、相对连续的 Redo，后续再由后台线程批量刷脏页。但 Redo 的首要目标仍是崩溃恢复与持久性。

### 14.2 Buffer Pool 中能否存在未提交数据？

可以。数据页在内存中被直接修改，是否对其他事务可见由锁、MVCC、Read View、事务状态和 Undo 版本链决定。

### 14.3 未提交事务的脏页能否落盘？

可以。WAL 要求的是相关 Redo 先于脏页落盘，不要求事务必须先提交。事务最终回滚或崩溃恢复时，由 Undo 撤销未提交修改。

### 14.4 Redo 持久化是否代表事务提交？

不代表。Redo 可能因刷脏、后台刷新、日志空间压力或 Group Commit 在事务提交前落盘。它只说明修改具备恢复依据。

### 14.5 恢复时会不会回放未提交事务？

可能会。InnoDB 先通过 Redo 恢复数据页的物理一致性，再根据事务和 Undo 状态识别未完成事务并回滚。

### 14.6 提交成功但数据页没落盘，会丢数据吗？

在正确的持久化配置下不会。已提交事务所需的 Redo 已经可靠持久化，崩溃后可以利用 Redo 将修改恢复到数据页。

### 14.7 Redo 已经落盘但事务没提交，宕机会怎样？

恢复时可能先通过 Redo 恢复相关页面，然后识别出该事务没有完成提交，再使用 Undo 撤销其修改。

## 15. 核心结论

1. Redo 是 InnoDB 的页级重做日志，用于持久性和崩溃恢复。
2. Redo 在数据修改时生成，不是等到 `COMMIT` 才生成。
3. WAL 要求 Redo 先于对应脏页落盘，不要求事务先提交。
4. Buffer Pool 和数据文件中都可能暂时存在未提交事务的修改。
5. 未提交事务的脏页可以刷盘，事务提交时也不强制立即刷新全部数据页。
6. Redo 持久化只代表修改具备恢复依据，不代表事务已经提交。
7. 崩溃恢复可能先回放未提交事务的页修改，再通过 Undo 撤销。
8. InnoDB 结合事务系统、Undo 和事务 ID 判断哪些事务需要回滚。
9. LSN 标识日志和页面进度，Checkpoint 决定旧 Redo 空间何时可以复用。
10. Redo、Undo、Binlog 分工不同，不能相互替代。

一句话总结：

> Redo Log 通过“日志先行、数据页后写”降低事务提交成本；崩溃后先恢复页面，再结合 Undo 和事务状态撤销未提交修改。
