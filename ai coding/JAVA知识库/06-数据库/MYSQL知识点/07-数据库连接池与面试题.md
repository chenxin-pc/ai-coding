## 1. 阶段目标

数据库连接池运行在应用侧，不是 MySQL 服务端组件。学习这一阶段后，应能够讲清：

```text
为什么不能频繁创建物理连接
  -> DataSource 和连接池是什么关系
  -> close() 为什么变成归还连接
  -> C3P0 到 HikariCP 的设计变化
  -> 生产参数如何配置
  -> 连接池满时怎样定位真正根因
```

连接池只能治理连接，不能替代 SQL、索引、事务和数据库容量优化。

## 2. 从 JDBC 到 HikariCP 的演进

### 2.1 原生 JDBC

最基础的方式是通过 `DriverManager` 创建连接：

```java
String url = "jdbc:mysql://localhost:3306/demo";

try (Connection connection =
         DriverManager.getConnection(url, "root", "password");
     PreparedStatement statement =
         connection.prepareStatement("SELECT * FROM user WHERE id = ?")) {

    statement.setLong(1, 1L);
    try (ResultSet resultSet = statement.executeQuery()) {
        // 处理结果
    }
}
```

一次物理连接可能经历：

```text
建立 TCP 连接
  -> MySQL 握手和身份认证
  -> 创建数据库会话
  -> 执行 SQL
  -> 关闭会话和 TCP 连接
```

如果每个请求都重新建立连接，会产生网络握手、认证、线程和会话创建成本，也无法统一限制数据库并发。

JDBC 4 以后驱动通常通过 SPI 自动注册，一般不再需要手工执行：

```java
Class.forName("com.mysql.cj.jdbc.Driver");
```

### 2.2 DataSource 抽象

`DataSource` 是 JDBC 推荐的连接获取标准接口：

```java
DataSource dataSource = ...;

try (Connection connection = dataSource.getConnection()) {
    // 执行数据库操作
}
```

需要区分：

- `DataSource` 是获取连接的抽象，不一定带连接池。
- 连接池通常实现 `DataSource`，使业务代码不依赖具体实现。
- `DriverManager` 根据 JDBC URL 直接创建连接。
- `DataSource` 更适合依赖注入、集中配置、JNDI、池化和分布式事务。

### 2.3 连接池原理

连接池维护一组可复用的物理连接：

```text
应用启动或首次请求
  -> 创建物理连接
  -> 放入空闲连接集合
  -> 业务调用 getConnection()
  -> 返回代理 Connection
  -> 业务调用 close()
  -> 恢复状态并归还连接池
```

连接池返回的通常是代理连接。业务调用 `close()` 时，代理对象把连接归还池中，而不是立即断开 MySQL 物理连接。

物理连接通常在以下情况关闭：

- 连接失效或有效性检测失败。
- 达到最大生命周期。
- 空闲超时并且超过最小空闲连接数。
- 数据库或网络已经断开。
- 连接池或应用关闭。

连接归还时还要恢复 `autoCommit`、只读状态、事务隔离级别、Catalog、Schema、网络超时等状态，防止影响下一个请求。

### 2.4 C3P0

C3P0 是较早流行的通用 JDBC 连接池，支持：

- 初始化、最小和最大连接数。
- `acquireIncrement` 批量扩容。
- 空闲连接检测和生命周期管理。
- PreparedStatement 缓存。
- JMX 监控和辅助排障。

典型配置思路：

```java
ComboPooledDataSource dataSource = new ComboPooledDataSource();
dataSource.setJdbcUrl("jdbc:mysql://localhost:3306/demo");
dataSource.setUser("root");
dataSource.setPassword("password");
dataSource.setInitialPoolSize(5);
dataSource.setMinPoolSize(5);
dataSource.setMaxPoolSize(20);
dataSource.setAcquireIncrement(5);
dataSource.setCheckoutTimeout(3000);
dataSource.setMaxIdleTime(600);
dataSource.setIdleConnectionTestPeriod(60);
```

C3P0 功能完整且仍可使用，但配置项较多、实现相对传统。现代 Spring Boot 项目通常优先使用配置更少、连接获取路径更轻量的 HikariCP。

### 2.5 HikariCP

HikariCP 的设计重点包括：

- 缩短连接借用和归还路径。
- 减少锁竞争和临时对象创建。
- 使用高效的 Connection、Statement 代理。
- 保留少量关键参数，减少复杂策略。
- PreparedStatement 缓存交给 JDBC 驱动处理。
- 推荐容量明确的固定大小连接池。

Spring Boot 在 HikariCP 可用时会优先使用它。连接获取流程为：

```text
请求连接
  -> 有空闲连接：返回代理连接
  -> 无空闲连接但未达到 maximumPoolSize：创建连接
  -> 已达到 maximumPoolSize：等待连接归还
  -> 超过 connectionTimeout：抛出 SQLException
```

HikariCP 性能好不等于可以忽略 SQL。大多数生产系统中，索引、事务范围、慢 SQL、锁竞争和容量规划的影响通常更大。

## 3. HikariCP 生产配置

### 3.1 Spring Boot 基线配置

下面是配置起点，不应直接照抄连接数和超时时间：

```yaml
spring:
  datasource:
    url: jdbc:mysql://mysql-host:3306/demo
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}
    hikari:
      pool-name: demo-hikari-pool
      maximum-pool-size: 20

      # 不配置时默认等于 maximumPoolSize，形成固定大小连接池
      # minimum-idle: 20

      connection-timeout: 3000
      validation-timeout: 1000
      max-lifetime: 1740000
      keepalive-time: 120000

      # 仅在 minimumIdle < maximumPoolSize 时影响缩容
      idle-timeout: 600000

      initialization-fail-timeout: 1
      leak-detection-threshold: 0
      register-mbeans: true

      data-source-properties:
        cachePrepStmts: true
        prepStmtCacheSize: 250
        prepStmtCacheSqlLimit: 2048
        useServerPrepStmts: true
        tcpKeepAlive: true
```

账号密码应由环境变量或密钥管理系统注入，不应提交到代码仓库。

### 3.2 核心参数

| 参数 | 默认值 | 含义与注意事项 |
|---|---:|---|
| `maximumPoolSize` | 10 | 最大物理连接总数，必须按数据库容量和全部实例计算 |
| `minimumIdle` | 等于最大连接数 | 最少空闲连接；通常省略，使用固定大小模式 |
| `connectionTimeout` | 30 秒 | 从池中获取连接的最长等待时间，最低 250ms |
| `validationTimeout` | 5 秒 | 检测连接有效性的超时，必须小于 `connectionTimeout` |
| `idleTimeout` | 10 分钟 | 动态池空闲连接回收时间，固定大小池基本不生效 |
| `maxLifetime` | 30 分钟 | 物理连接最大生命周期，最低 30 秒 |
| `keepaliveTime` | 2 分钟 | 对空闲连接进行保活，必须小于 `maxLifetime` |
| `leakDetectionThreshold` | 0 | 连接长时间未归还时记录日志，0 表示关闭 |
| `autoCommit` | true | 返回连接时的默认自动提交行为，通常由事务框架管理 |

#### maximumPoolSize

它控制单个连接池的最大物理连接数。不能只根据接口并发量设置，还要计算全部应用实例、其他服务和运维连接。

#### connectionTimeout

这是等待连接池中可用连接的时间，不是 TCP 建连时间，也不是 SQL 执行时间：

```text
Hikari connectionTimeout：等待池中连接
Connector/J connectTimeout：建立 TCP 连接
Connector/J socketTimeout：建连后等待数据库网络响应
```

#### maxLifetime

应小于数据库、代理、防火墙、NAT 和负载均衡器中最短的连接期限：

```text
maxLifetime < min(
    MySQL wait_timeout,
    代理空闲超时,
    负载均衡器空闲超时,
    防火墙或 NAT 超时
)
```

例如基础设施会在 30 分钟关闭连接，可以将 `maxLifetime` 设置为约 29 分钟。若最短期限只有 10 分钟，应设置为略小于 10 分钟，而不是继续使用 30 分钟。

#### keepaliveTime

HikariCP 只会对空闲连接执行保活。它应小于外部空闲超时和 `maxLifetime`，但不能替代合理的生命周期配置、TCP keepalive 和故障恢复设计。

#### connectionTestQuery

现代 MySQL Connector/J 支持 JDBC 4 的 `Connection.isValid()`，通常不需要设置：

```yaml
connection-test-query: SELECT 1
```

只有旧驱动不支持 `isValid()` 时才考虑测试 SQL。

#### leakDetectionThreshold

连接借出超过阈值仍未归还时，HikariCP 会输出借出位置的堆栈。它只能说明连接持有时间过长，不一定是真泄漏。

以下情况也可能触发：

- 合法的长事务。
- 慢 SQL 或锁等待。
- 大批量任务。
- 事务中调用远程接口。
- 流式读取大结果集。

阈值应高于正常连接持有时间的 P99。排查结束后可关闭，避免误报和额外日志。

### 3.3 MySQL 驱动参数

HikariCP 不提供连接池级 PreparedStatement 缓存，通常使用 Connector/J 的每连接缓存：

```yaml
data-source-properties:
  cachePrepStmts: true
  prepStmtCacheSize: 250
  prepStmtCacheSqlLimit: 2048
  useServerPrepStmts: true
```

其他参数需要按场景评估：

```yaml
data-source-properties:
  connectTimeout: 3000
  socketTimeout: 15000
  tcpKeepAlive: true
  rewriteBatchedStatements: true
```

注意事项：

- `socketTimeout` 必须覆盖正常最长 SQL，不能机械照抄。
- `rewriteBatchedStatements` 只对实际使用 JDBC 批处理的场景有意义。
- 不建议依赖 `autoReconnect=true`，事务中悄悄换连接会丢失会话和事务状态。
- TLS、时区、字符集等参数应依据数据库和安全要求配置。
- 驱动参数调整后需要用真实 SQL 和并发模型压测。

## 4. 连接池容量规划

### 4.1 集群总量

```text
数据库潜在连接总数
= 服务 A 实例数 × A 的 maximumPoolSize
+ 服务 B 实例数 × B 的 maximumPoolSize
+ 定时任务、报表和数据同步连接
+ 运维和监控连接
```

所有业务连接池上限之和不能直接占满 MySQL `max_connections`，还要为发布扩容、故障重连和管理操作保留余量。

例如：

```text
10 个实例 × 每实例 30 个连接 = 300 个潜在连接
```

滚动发布时新旧实例可能短暂同时存在，潜在连接数还会继续增加。

### 4.2 业务需求

可以使用 Little's Law 做初步估算：

```text
并发连接需求 ≈ 峰值 TPS × P95 连接持有时间（秒）
```

例如峰值 2000 TPS，P95 连接持有时间为 10ms：

```text
2000 × 0.01 = 20 个并发连接
```

连接持有时间包括整个事务期间的 SQL、程序处理、提交或回滚时间，不只是单条 SQL 的执行时间。

### 4.3 压测验证

逐步增加池大小，例如：

```text
10 -> 20 -> 30 -> 50
```

同时比较 TPS、P95/P99、连接等待、MySQL CPU、磁盘 I/O、锁等待和慢 SQL。当增加连接后吞吐不再提升，但延迟和资源竞争开始恶化，就接近数据库并发拐点。

连接池的职责之一是保护数据库，因此不是越大越好。

## 5. 生产监控

HikariCP 至少监控：

| 指标 | 含义 | 关注点 |
|---|---|---|
| `Active` | 正在使用的连接数 | 是否长时间达到最大值 |
| `Idle` | 空闲连接数 | 是否长期为 0 或明显过多 |
| `Total` | 连接总数 | 是否符合预期 |
| `Pending` | 等待连接的线程数 | 持续大于 0 需要告警 |
| `Acquire` | 获取连接耗时 | P95/P99 是否上升 |
| `Usage` | 连接持有时间 | 是否出现长事务或慢查询 |
| `Creation` | 创建物理连接耗时 | 网络、认证和数据库是否异常 |
| `Timeout` | 获取连接超时次数 | 正常情况下应为 0 |

MySQL 同时检查：

```sql
SHOW GLOBAL STATUS WHERE Variable_name IN (
    'Threads_connected',
    'Threads_running',
    'Max_used_connections',
    'Connection_errors_max_connections',
    'Aborted_connects',
    'Aborted_clients'
);
```

基础告警可以从以下条件开始，再根据业务基线调整：

- `Pending > 0` 持续一分钟。
- `Active == Maximum` 持续出现。
- 获取连接超时次数增加。
- 获取连接或持有时间 P95/P99 明显上涨。
- `Connection_errors_max_connections` 增长。
- MySQL `Threads_running`、慢 SQL 和锁等待同时上升。

## 6. 常见问题排查

### 6.1 获取连接超时

典型异常：

```text
HikariPool - Connection is not available,
request timed out after 3000ms
```

排查顺序：

```text
Active 是否达到 Maximum
  -> Pending 是否持续增长
  -> 连接持有时间是否上涨
  -> 是否有慢 SQL、锁等待和长事务
  -> 是否存在连接未关闭
  -> 事务中是否调用远程接口
  -> 数据库仍有余量时才评估扩大连接池
```

数据库已过载时扩大连接池，通常只会让更多请求同时压入数据库。

### 6.2 Communications link failure

常见原因：

- MySQL 重启、宕机或主备切换。
- DNS、网络、防火墙或代理异常。
- 网络设备清理空闲连接。
- `maxLifetime` 大于基础设施连接期限。
- TCP keepalive 不合理。
- SQL 超过 `socketTimeout`。

需要对齐应用异常时间、MySQL 日志、代理日志和网络监控，而不是仅修改连接池参数。

### 6.3 Apparent connection leak detected

泄漏日志中的堆栈是连接借出位置。重点检查：

- JDBC 资源是否全部关闭。
- `@Transactional` 是否包含远程调用或耗时计算。
- 是否跨异步线程传递连接。
- 流式 ResultSet 是否长期未消费完。
- 是否存在慢 SQL 或锁等待。
- 阈值是否低于正常业务耗时。

### 6.4 Too many connections

先收集证据：

```sql
SHOW VARIABLES LIKE 'max_connections';
SHOW GLOBAL STATUS LIKE 'Threads_connected';
SHOW GLOBAL STATUS LIKE 'Max_used_connections';
SHOW GLOBAL STATUS LIKE 'Connection_errors_max_connections';

SELECT USER, HOST, COMMAND, COUNT(*) AS connection_count
FROM information_schema.PROCESSLIST
GROUP BY USER, HOST, COMMAND
ORDER BY connection_count DESC;
```

重点检查实例扩容、重复连接池、其他服务占用、大量 Sleep 连接，以及是否存在绕过连接池直接建连的代码。

### 6.5 Active 很高但 Threads_running 很低

通常表示应用借出了连接，却没有持续执行 SQL：

- 事务中执行耗时 Java 逻辑。
- 等待 HTTP、RPC 或消息结果。
- 未及时提交或回滚。
- 流式处理大结果集。
- 连接没有正常归还。

应缩短连接持有时间，而不是首先扩大连接池。

### 6.6 Active 和 Threads_running 都很高

通常意味着数据库正在承受真实并发，重点检查：

- 慢 SQL 和缺失索引。
- 大量排序、聚合和临时表。
- 行锁、间隙锁或元数据锁等待。
- CPU 或磁盘 I/O 饱和。
- 大事务和批处理任务。

此时连接池只是暴露数据库瓶颈，应优先治理 SQL、事务和数据库资源。

## 7. 高频面试题

### 7.1 JDBC 与连接池基础

#### 1. JDBC 访问数据库的基本步骤是什么？

加载或自动发现驱动，获取 Connection，创建 PreparedStatement，绑定参数，执行 SQL，处理 ResultSet，最后关闭结果集、语句和连接。现代项目一般通过 DataSource 获取连接，并使用 `try-with-resources` 或 Spring 管理资源。

#### 2. 为什么 JDBC 4 以后通常不需要 Class.forName？

JDBC 4 支持 SPI 自动加载。驱动 JAR 可以通过 `META-INF/services/java.sql.Driver` 声明驱动实现，`DriverManager` 自动发现并注册。

#### 3. DriverManager 和 DataSource 有什么区别？

`DriverManager` 主要根据 JDBC URL 直接创建连接；`DataSource` 是标准抽象，适合集中配置、依赖注入、JNDI、池化和分布式事务。DataSource 不一定自带连接池。

#### 4. 为什么推荐 PreparedStatement？

它使用参数绑定，降低 SQL 注入风险，避免手工转义，并可能利用驱动或数据库的执行计划缓存。表名、列名和排序方向不能通过普通占位符绑定，仍要进行白名单校验。

#### 5. 为什么需要连接池？

物理连接建立成本较高。连接池通过复用连接降低握手和认证开销，同时提供数据库并发控制、超时、检测、回收、泄漏诊断和监控能力。

#### 6. Connection.close() 会真的关闭连接吗？

原生 JDBC 通常关闭物理连接；连接池返回的一般是代理连接，`close()` 表示归还。失效、超龄、空闲回收或连接池关闭时才真正关闭物理连接。

#### 7. 为什么连接池要返回代理 Connection？

代理可以拦截 `close()`、记录连接借出时间、检测泄漏、跟踪状态变化，并在归还时恢复连接状态。

#### 8. C3P0 和 HikariCP 有什么区别？

C3P0 功能丰富、参数较多，支持自身的 Statement 缓存和批量扩容；HikariCP 更轻量，优化连接获取和代理路径，配置更少，并把 PreparedStatement 缓存交给驱动。Spring Boot 默认优先使用 HikariCP。

#### 9. HikariCP 为什么性能较好？

主要原因是连接借还路径短、锁竞争和临时对象较少、代理实现高效、功能边界清晰。但生产性能通常更取决于 SQL、索引、事务和数据库资源。

#### 10. HikariCP 为什么不自己缓存 PreparedStatement？

PreparedStatement 与物理连接绑定，连接池级缓存容易随连接数和 SQL 数量膨胀。HikariCP 推荐使用 Connector/J 的每连接缓存。

### 7.2 HikariCP 参数

#### 11. maximumPoolSize 和 minimumIdle 有什么区别？

`maximumPoolSize` 是连接总数上限；`minimumIdle` 是希望维持的最少空闲连接数。HikariCP 不设置 `minimumIdle` 时，它默认等于最大连接数，形成固定大小池。

#### 12. 连接池满了以后会怎样？

新线程等待其他线程归还连接；超过 `connectionTimeout` 后抛出获取连接超时异常。连接池不会无限创建连接。

#### 13. connectionTimeout、connectTimeout 和 socketTimeout 有什么区别？

分别表示等待池中连接、建立 TCP 连接、建连后等待数据库网络响应。三者属于不同层次，不能互相替代。

#### 14. idleTimeout 和 maxLifetime 有什么区别？

`idleTimeout` 控制多余空闲连接何时缩减，只有动态池才有意义；`maxLifetime` 控制物理连接最长生命周期。正在使用的连接不会因达到生命周期被强行中断，而是在归还后淘汰。

#### 15. keepaliveTime 有什么作用？

它定期检测空闲连接，降低连接被数据库或网络基础设施静默关闭的概率。它必须小于 `maxLifetime`，并应小于外部空闲连接超时。

#### 16. 为什么通常不配置 connectionTestQuery？

现代 Connector/J 支持 JDBC 4 `Connection.isValid()`。HikariCP 可以直接调用它，旧驱动不支持时才需要测试 SQL。

#### 17. leakDetectionThreshold 是什么？

连接借出超过阈值时输出疑似泄漏日志。它是诊断信号，不是泄漏的最终结论，慢 SQL、锁等待和合法长事务也可能触发。

#### 18. 为什么不推荐 autoReconnect=true？

事务中自动换连接会丢失原连接上的事务、锁、临时表和会话变量状态。应让当前操作失败，由连接池淘汰坏连接，再按照幂等性决定是否重试整个业务操作。

### 7.3 容量与事务

#### 19. 连接池是不是越大越好？

不是。连接过多会增加 MySQL 线程调度、内存、上下文切换、磁盘 I/O 和锁竞争。连接池还承担数据库限流和保护作用。

#### 20. 连接池大小如何评估？

先用峰值 TPS 与连接持有时间估算业务需求，再计算全部实例连接池总和，确认小于数据库容量，最后通过压测寻找吞吐量不再增加而延迟开始恶化的拐点。

#### 21. MySQL max_connections=500，应用池能设置成 500 吗？

通常不能。要计算实例数量、其他服务、报表、同步、运维和发布扩容，并为故障恢复保留余量。单实例 500 在多实例环境会迅速超过数据库上限。

#### 22. 大量 Sleep 连接一定有问题吗？

不一定。连接池中的空闲物理连接在 MySQL 中通常显示为 Sleep。需要判断数量是否符合全部连接池配置、是否挤占上限，以及是否存在异常超长连接或重复创建连接池。

#### 23. 什么是连接池资源死锁？

线程持有一个连接后又申请第二个连接，多个线程可能各自持有部分连接并等待剩余连接。若有 `T` 个线程、每个线程最多同时持有 `C` 个连接，避免资源死锁的理论下限为：

```text
pool size = T × (C - 1) + 1
```

更好的方案通常是避免单线程同时持有多个独立连接。

#### 24. Spring 事务中连接什么时候归还？

进入事务后，Spring 将连接绑定到事务上下文；事务提交或回滚并完成清理后，连接才归还池中。因此事务范围直接影响连接持有时间。

#### 25. 为什么不应在数据库事务中调用远程接口？

等待远程调用期间，连接和数据库锁可能一直被占用，导致连接池耗尽、锁时间增长和故障放大。应缩短事务，只在必要数据库操作期间持有连接。

### 7.4 生产场景题

#### 26. 连接池突然满了，是否应该立即扩容？

不应。先检查慢 SQL、锁等待、长事务、连接泄漏、流式查询和事务中的远程调用。只有确认数据库仍有容量、SQL 和连接持有时间正常时，才考虑增加连接数。

#### 27. Active 很高但 Threads_running 很低说明什么？

连接被应用借走，但没有持续执行 SQL，可能在事务中计算、等待远程服务、流式处理结果，或没有及时提交和归还。应查看连接持有时间和 JVM 线程栈。

#### 28. Active 和 Threads_running 都很高说明什么？

数据库正在承受真实并发。应检查慢 SQL、索引、排序、临时表、锁等待、CPU 和磁盘 I/O，而不是只调整连接池。

#### 29. 如何证明连接池太小，而不是 SQL 太慢？

需要看到 Active 经常达到最大值、Pending 和获取连接耗时上涨，同时 SQL 执行时间正常、MySQL CPU/IO/锁仍有余量，并且小幅增加连接后 TPS 提升且数据库延迟没有恶化。

#### 30. 发布扩容后为什么可能出现 Too many connections？

滚动发布期间新旧实例同时存在。如果 10 个实例每个池 30，正常理论上限是 300；发布期间短暂出现 20 个实例，就可能达到 600。容量规划必须考虑实例重叠。

#### 31. Communications link failure 如何排查？

对齐 MySQL 重启或切换、网络和 DNS、代理空闲超时、`wait_timeout`、`maxLifetime`、TCP keepalive 和 `socketTimeout`。不能仅凭异常文本认定是连接池问题。

#### 32. 出现连接泄漏日志如何定位？

从借出堆栈定位业务入口，再检查资源关闭、事务边界、远程调用、异步线程、流式结果、慢 SQL 和锁等待，并确认泄漏阈值是否合理。

#### 33. 数据库重启后 HikariCP 会怎样？

旧连接检测失败后会被淘汰，连接池继续尝试创建新连接。正在执行的事务仍会失败，应用还需要合理的超时、有限重试、退避、幂等和就绪检查。

#### 34. 接口大量超时但数据库 CPU 不高，如何排查？

先看 HikariCP Active、Idle、Pending、获取耗时和持有时间，再看 JVM 线程栈、数据库锁等待、网络和代理。锁等待、连接泄漏和网络异常都可能表现为低 CPU、高延迟。

#### 35. 为什么扩大连接池后问题可能更严重？

如果根因是慢 SQL、锁竞争或数据库资源饱和，扩大连接池会允许更多请求同时进入数据库，进一步增加排队、锁和资源竞争。

#### 36. HikariCP 能否实现读写分离和故障转移？

不能。HikariCP 负责连接生命周期和池化，不负责 SQL 路由、主从拓扑和业务级故障转移。这些能力需要数据库驱动、代理、中间件或应用架构配合。

## 8. 一分钟回答模板

> 原生 JDBC 每次创建物理连接需要 TCP 握手、认证和会话初始化，因此通过实现 DataSource 的连接池复用连接。连接池返回代理 Connection，业务调用 close() 时通常是归还连接，并重置事务和会话状态。C3P0 是早期功能丰富的连接池，HikariCP 通过精简功能、优化并发和代理路径成为 Spring Boot 的默认选择。生产上重点配置 maximumPoolSize、connectionTimeout、maxLifetime 和 keepaliveTime，连接数要结合全部实例、数据库容量、连接持有时间和压测确定。出现池耗尽时不能直接扩容，应先排查慢 SQL、锁等待、长事务、远程调用和连接泄漏。
