## 1. MySQL 架构

MySQL 可以按连接管理、SQL 处理、数据存储三个部分理解。其中，连接管理本身属于 Server 层，单独列出是为了便于理解。

```text
客户端：应用程序 / JDBC / 数据库工具
    ↓
Server 层
    连接管理、身份认证、会话状态、权限检查
    SQL 解析与预处理 → 优化器 → 执行器
    Binlog
    ↓ 存储引擎接口
InnoDB 存储引擎
    数据页、索引、事务、锁、MVCC
    Buffer Pool、Redo Log、Undo Log
    ↓
磁盘：表空间与日志文件等
```

| 组件 | 主要职责 |
|---|---|
| 连接管理 | 建立连接、身份认证、维护会话与连接生命周期 |
| 解析与预处理 | 解析 SQL 语法，解析和检查表、字段等引用 |
| 优化器 | 选择索引、访问方式、连接顺序等，生成执行计划 |
| 执行器 | 按计划调用存储引擎，处理剩余过滤、连接、聚合等操作 |
| InnoDB | 组织和访问数据，提供事务、并发控制与崩溃恢复能力 |

SQL 描述“要什么数据”，执行计划决定“如何获取数据”。过滤不只发生在执行器中，也可能发生在存储引擎中。

MySQL 8.0 已移除旧版 Query Cache；不要把它与缓存数据页、索引页的 Buffer Pool 混淆。

## 2. 内存与日志

Buffer Pool 缓存数据页和索引页。读取时优先访问缓存，未命中再加载磁盘页；修改后尚未刷回数据文件的页称为脏页。

| 日志 | 所属层 | 核心用途 |
|---|---|---|
| Redo Log | InnoDB | 保存重做信息，支持崩溃恢复 |
| Undo Log | InnoDB | 保存撤销修改所需的信息，支持事务回滚与 MVCC |
| Binlog | Server | 记录数据变更事件，支持复制及配合备份进行时间点恢复 |

WAL 的核心是：修改后的数据页落盘前，相应的重做日志必须先持久化。提交事务通常不需要等待所有脏页落盘，日志的落盘要求取决于持久化配置。

一条更新的简化主线：

```text
解析 SQL、生成执行计划
    → InnoDB 定位记录并获取所需的锁
    → 记录 Undo、修改缓存页并生成 Redo
    → 开启 Binlog 时，通过内部两阶段提交协调提交状态
    → 按配置完成日志持久化并提交
    → 脏页随后在需要时刷回数据文件
```

## 3. 数据过滤发生在哪里

需要区分三种作用：

1. **索引定位**：使用查询条件确定索引访问范围，减少候选记录。
2. **索引条件过滤**：扫描索引项时，直接利用其中的字段判断条件，在回表前淘汰记录。
3. **剩余条件过滤**：存储引擎返回记录后，由 Server 层继续判断未下推的条件。

索引条件下推（Index Condition Pushdown，ICP）对应第二种：Server 将能够仅凭索引字段判断且满足下推要求的条件交给存储引擎，在读取完整行之前执行。

假设 `users` 表有主键 `id`，联合二级索引 `(city, name)`，`address` 不在该索引中。查询示例：

```sql
SELECT *
FROM users
WHERE city = '深圳'
  AND name LIKE '%明%'
  AND address LIKE '%科技园%';
```

假设优化器选择该联合索引并使用 ICP，分工如下：

| 条件 | 处理位置 | 作用 |
|---|---|---|
| `city = '深圳'` | InnoDB 索引访问过程 | 定位联合索引中 city 为深圳的范围 |
| `name LIKE '%明%'` | InnoDB，回表之前 | 使用索引中的 name 过滤候选索引项 |
| `address LIKE '%科技园%'` | Server 层执行器 | 获取完整行后判断剩余条件 |

`name LIKE '%明%'` 不能用于普通 B+Tree 的范围定位，但索引中存有 name，因此可以扫描索引项并判断条件。**不能缩小索引扫描范围，不等于不能利用索引字段过滤。**

## 4. 索引下推的执行过程

InnoDB 二级索引叶子节点保存索引列值和主键值；根据主键访问聚簇索引、获取完整行的过程称为回表。

不使用 ICP 时，上例的简化流程：

```text
InnoDB：定位 city = '深圳' 的索引范围
    ↓
InnoDB：读取一个索引项，根据主键回表取得完整行
    ↓
Server：判断 name 和 address 条件
    ↓
继续读取下一条候选记录
```

使用 ICP 时：

```text
InnoDB：定位 city = '深圳' 的索引范围
    ↓
InnoDB：读取一个索引项，判断 name 是否包含“明”
    ├─ 不符合 → 跳过，不回表
    └─ 符合   → 根据主键回表读取完整行
                    ↓
Server：判断 address 是否包含“科技园”
```

假设深圳有 1,000 条记录，其中 100 条的 name 包含“明”，最后 10 条满足 address 条件。以下是解释机制的假设数据，不是实测结果：

| 操作 | 不使用 ICP | 使用 ICP |
|---|---:|---:|
| 扫描候选二级索引项 | 1,000 条 | 1,000 条 |
| 回表读取完整行 | 1,000 次 | 100 次 |
| 返回给 Server 继续过滤 | 1,000 条 | 100 条 |
| 最终结果 | 10 条 | 10 条 |

本例中，ICP 减少回表次数和向 Server 返回的候选记录数，没有缩小二级索引扫描范围。回表不等于一定读取磁盘，聚簇索引页可能已经在 Buffer Pool 中。

## 5. 执行计划与常见误区

给上面的查询加上 `EXPLAIN`，观察所选索引和 `Extra`：

| 标记 | 含义 |
|---|---|
| `Using index condition` | 使用索引条件下推 |
| `Using index` | 通常表示覆盖索引，可从索引获得查询所需数据 |
| `Using where` | 存在进一步的条件过滤；可以与其他标记一起出现 |

不要仅凭 `Using where` 判断索引未生效，应结合 `key`、访问类型和完整执行计划。

几个容易混淆的点：

- **ICP 下推的是条件**：从 Server 层交给存储引擎判断，不是把索引移到其他位置。
- **ICP 与覆盖索引不同**：ICP 先筛选，再对通过的记录回表；覆盖索引从索引取得所需数据，通常不需要为获取字段而回表。
- **InnoDB 的 ICP 用于二级索引**：聚簇索引叶子节点已经包含完整行，不能通过同样方式节省回表。
- **并非索引上的所有条件都能下推**：包含子查询或存储函数等条件存在限制。
- **默认开启不代表每条 SQL 都使用**：是否采用 ICP 取决于访问路径、查询条件等，必须查看执行计划。

## 6. 面试回答模板

> MySQL 的数据过滤可以发生在 Server 层，也可以发生在存储引擎层。先通过索引访问条件定位候选范围，再由 InnoDB 利用下推的索引条件过滤，剩余条件交给 Server 判断。索引下推的核心是利用二级索引中已有的字段，在回表前淘汰不满足条件的记录，从而减少回表。例如联合索引 `(city, name)`，city 等值用于定位，name 的包含匹配虽然不能进一步缩小扫描范围，但可以用于下推过滤。执行计划中可通过 `Using index condition` 识别 ICP。
