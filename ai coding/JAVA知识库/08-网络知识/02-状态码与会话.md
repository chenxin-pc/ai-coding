## 05. 常见状态码有哪些？301/302、401/403、502/504 如何区分？

### 是什么

状态码描述一次 HTTP 请求的处理结果，客户端和代理可以据此采用统一的处理方式。

| 类别 | 含义 | 需要记住的状态码 |
|---|---|---|
| 1xx | 阶段性信息 | 100：可以继续发送请求体 |
| 2xx | 成功 | 200：成功；201：已创建；204：成功且无响应体 |
| 3xx | 重定向或条件缓存处理 | 301：永久重定向；302：临时重定向；304：复用已有缓存 |
| 4xx | 请求或访问条件存在问题 | 400：请求有误；401：缺少有效认证；403：拒绝访问；404：未找到；429：请求过多 |
| 5xx | 服务端无法完成请求 | 500：内部错误；502：上游响应无效；503：暂时不可用；504：等待上游超时 |

### 为什么

状态码让认证、重定向、缓存和失败处理不依赖某个系统的业务响应体。以下三组区别需要能直接解释：

- **301 与 302：** 前者表示永久迁移，后者表示临时跳转；重定向地址通常在 Location 中。两者都不能作为“保证保留 POST 方法和请求体”的依据。
- **401 与 403：** 401 主要解决有效认证缺失，标准响应应带 WWW-Authenticate；403 表示理解请求但拒绝处理，常见原因是权限或访问策略。
- **502 与 504：** 前者是代理收到无效上游响应，后者是代理等上游超时。需要找出是哪一层生成了错误。

### 实际场景怎么用或排查

401 检查 Token、有效期和网关是否透传认证头；403 检查角色、资源归属、租户权限和安全拦截规则。

502 检查上游重启、连接重置、响应格式与代理协议配置；504 检查上游耗时、线程池或连接池排队、慢 SQL 和各层超时。用请求 ID 串联客户端、网关和服务日志，不要只扩大 timeout。

**易错点：** HTTP 200 不必然代表应用定义的业务成功；304 没有响应体；504 不证明订单没有创建。状态码分类也不直接等同于故障责任归属。

参考 [HTTP 状态码](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Reference/Status)、[重定向](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Redirections)和 [401](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/401)。

## 06. HTTP 为什么无状态？如何保持登录状态？

### 是什么

HTTP 无状态是指协议没有自动为多次请求维持“已登录用户上下文”。应用可以在每次请求中传入身份信息，结合服务端状态或可验证凭据建立会话。

### 为什么

请求不必绑定前一次请求或某条 TCP 连接，有利于连接切换和请求分发。登录态属于应用设计，需要自己明确创建、验证、过期和注销规则。

### 实际场景怎么用或排查

典型流程：登录验证成功 → 服务端建立 Session → 通过 Set-Cookie 返回随机会话标识 → 后续请求携带 Cookie → 服务端查 Session 识别用户。也可以每次携带访问 Token，再验证其有效性。

多实例部署后“时好时坏地掉登录”，检查会话是否只存在某一实例内存、请求是否切换实例、会话存储是否共享，以及 Cookie 域和路径是否正确。可根据规模选择共享会话或其他明确的会话管理方案。

**易错点：** 长连接不等于已登录；换一条连接不应自动丢登录；“HTTP 无状态”不意味着服务器不能存储状态。参考 [HTTP 无状态与会话](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Guides/Overview#http_无状态，但并非无会话)。

## 07. Cookie、Session、Token 有什么区别？

### 是什么

| 概念 | 主要职责 | 典型形态 |
|---|---|---|
| Cookie | 浏览器存储和按规则发送少量数据的机制 | 会话 ID、偏好设置 |
| Session | 应用维护的一段会话状态 | 服务端记录用户、权限、过期时间 |
| Token | 表示某种凭据或授权的数据 | 不透明随机串、带签名的 JWT |

它们不是互斥选项：Cookie 可以装 Session ID，也可以装 Token；Token 也可以通过 Authorization 发送。

### 为什么

存储位置、发送方式、验证方式是三个不同维度。服务端 Session 便于集中失效，但要维护状态；自包含 Token 可减少部分查询，但撤销、权限变更和密钥轮换需要额外设计。

### 实际场景怎么用或排查

浏览器会话 Cookie 常设置 Secure（安全传输）、HttpOnly（限制脚本读取）和合适的 SameSite（约束跨站发送），但这些属性不能替代完整的权限与 CSRF 防护。

浏览器登录常使用带安全属性的 Cookie；服务间调用可按认证方案发送 Bearer Token。注销时明确是只清除客户端凭据，还是同时让服务端会话、刷新凭据或访问凭据失效。

**易错点：** JWT 是一种令牌格式，不代表一定不需要服务端状态；常见签名 JWT 的载荷能被解码，签名不等于加密。校验不能只解码，还需要验证签名、算法、有效期及受众等约束。Cookie 机制参考 [Using HTTP cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)，JWT 定义参考 [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html)。
