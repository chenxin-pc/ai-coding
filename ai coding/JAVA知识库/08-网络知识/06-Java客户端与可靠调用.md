## 16. HTTP 连接池有什么作用？连接耗尽时如何排查？

### 是什么

HTTP 连接池管理可复用的连接，并限制资源占用。请求获取连接、发送消息、消费响应，处理结束后释放相关资源，使符合复用条件的连接可供后续请求使用。

HTTP/1.1 的常见客户端通常在一条连接上顺序执行请求；HTTP/2 则可以在同一连接中并发多个流，因此连接数量不能直接等同于请求并发数。

### 为什么

每次调用都新建连接，会反复支付 TCP、TLS 等建连成本；DNS 是否重新查询还取决于缓存。复用长期存活、可安全共享的客户端实例通常有助于复用连接，但连接池也可能因响应未释放、下游变慢或容量不足而耗尽。

### 实际场景怎么用或排查

1. 先查看总连接数、每个目标的连接上限、已占用数、空闲数和等待请求数。
2. 已占用数长期不下降：检查响应体是否正确消费或关闭，尤其是异常、提前返回和流式读取路径。
3. 请求处理时间同时变长：检查下游慢接口、数据库等待及大响应传输，判断是否因连接占用时间增加导致排队。
4. 总池仍空闲但某目标等待严重：检查该目标的连接限制，HTTP/2 还需检查流并发上限。
5. 根据实际负载、下游承受能力和压测结果调整容量，并配置合理的空闲连接回收。

**易错点：** 释放响应资源不保证底层连接一定保留，客户端可能关闭不能安全复用的连接。不要每请求都关闭共享客户端，也不要把扩大池容量当成修复连接泄漏的方法。

连接池原理参考 [Apache HttpClient 4.5 连接管理](https://hc.apache.org/httpcomponents-client-4.5.x/current/tutorial/html/connmgmt.html)。该资料用于说明机制，具体 API、默认值及 HTTP/2 行为要按实际客户端版本确认。

## 17. 连接超时、读取超时、获取连接超时和整个请求超时有什么区别？

### 是什么

| 超时类型 | 限制的主要阶段 | 常见排查方向 |
|---|---|---|
| 获取连接超时 | 等待连接池分配可用资源 | 池满、单目标限制、资源未释放 |
| 连接超时 | 建立新连接 | 网络不通、目标不可达、建连过慢 |
| 读取超时 | 等待读取响应数据；很多实现针对一次阻塞读取 | 下游处理慢、传输停顿、网络问题 |
| 整体请求超时或 deadline | 从调用开始到完成的总时间预算 | 排队、各阶段、重试和退避的累积耗时 |

DNS、代理建连、TLS、流式消费是否计入某个 timeout，取决于客户端和版本，不能凭参数名推断全部覆盖范围。

### 为什么

不同阶段对应不同瓶颈。只设置连接超时，不能限制服务端业务执行时间；只设置读取超时，也可能在对端持续缓慢发送少量数据时等很久。整体时限用于约束用户能接受的总等待时间。

### 实际场景怎么用或排查

先看完整异常链，再结合连接池指标和分阶段耗时判断。Apache HttpClient 4.5 分别有 connectionRequestTimeout、connectTimeout、socketTimeout；JDK HttpClient 的建连超时与请求 timeout 是不同设置，不能机械套用另一库的参数。

入口只允许等待 3 秒，就不能给每次下游调用各分配 3 秒后再重试两次。应传递剩余时间预算，为本地处理、连接等待和重试留出空间；到期后正确取消本地调用并释放资源。对于流式响应，需要单独确认内容消费阶段也有合适的时限。

**易错点：** 本地超时或取消不代表远端事务回滚。连接已复用时，建连 timeout 通常不参与该次请求。

参数依据见 [Apache RequestConfig](https://hc.apache.org/httpcomponents-client-4.5.x/current/httpclient/apidocs/org/apache/http/client/config/RequestConfig.html)、[JDK 21 HttpClient.Builder](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpClient.Builder.html)和 [HttpRequest.Builder](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpRequest.Builder.html)。

## 18. HTTP 超时后能否重试？下单、支付接口如何保证幂等？

### 是什么

超时表示调用方在规定时间内没有取得所需结果，不能直接说明服务端是否完成业务。可能是请求没有送达，也可能已经提交订单，只是响应丢失或延迟。

幂等重试要求多次提交同一个业务操作，产生与一次执行相同的预期效果。HTTP 方法的幂等语义与业务实现必须一致；POST 也可以通过稳定的业务请求号实现幂等。

### 为什么

分布式调用无法仅从一次网络异常判断远端最终状态。重试提高可用性，也可能重复扣款、重复下单，或在服务过载时放大流量。

### 实际场景怎么用或排查

先按条件决定是否重试：

| 情况 | 处理方式 |
|---|---|
| 明确的参数错误或权限拒绝 | 先修正原因，不盲目原样重试 |
| 查询遇到暂时网络故障 | 在确认实际语义允许后进行有限重试 |
| 写操作的结果未知 | 先按业务号查结果，或使用同一幂等键重试 |
| 下游明确限流或暂不可用 | 结合约定、Retry-After、退避及剩余时限处理 |

一个常用的业务设计如下，属于应用方案，不是 HTTP 自动提供的能力：

1. 同一业务操作使用稳定请求号；每次重试保持不变，并按租户、操作类型等限定作用范围。
2. 保存关键参数摘要；同一个请求号若对应不同金额或商品，拒绝处理，避免误复用。
3. 通过数据库唯一约束或等价的原子机制阻止并发重复执行；不能只“先查询，没有再插入”。
4. 本地数据库操作尽量把幂等记录、业务写入和结果保存放在同一事务中，避免业务已成功但幂等记录丢失。
5. 已成功的重复请求返回原业务结果；处理中或结果未知时提供查询和恢复流程，不能直接作为失败重新扣款。
6. 涉及外部支付时，继续向支付方传递稳定业务号，并结合支付查询、回调和对账确认结果；本地事务不能覆盖远端执行。

重试应限制次数、采用退避和适当抖动，并受整体时限约束。检查网关、客户端、业务层是否各自重试，避免次数叠乘；确认上传流等请求体是否可重放。

**易错点：** 新生成一个幂等键再重试等于发起新操作；短期缓存去重不能替代长期业务唯一性；分布式锁本身也不能消除“外部操作已完成、本地进程崩溃”的不确定窗口。

业务契约可参考 [Stripe 的幂等请求设计](https://docs.stripe.com/api/idempotent_requests)，其键保留时间、失败结果处理等属于该服务自己的规则，不能直接当成所有接口的通用约定。
