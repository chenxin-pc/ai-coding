## 1. 用一句话理解火焰图

火焰图是一张程序运行时的开销分布图，帮助我们从“系统有性能问题”，找到“哪些调用路径值得重点检查”。

可以记住这条主线：

```text
监控发现异常
  -> 选择合适的采样类型
  -> 火焰图定位热点或等待路径
  -> 结合代码和其他数据确认原因
  -> 优化后验证实际效果
```

火焰图负责展示，Profiler 负责采集。它不会自动告诉我们代码应该怎么改。

## 2. 数据从哪里来

以 CPU 火焰图为例，工具在 Java 程序运行期间，多次给线程调用栈“拍快照”，记录线程当时执行到哪个方法，以及由谁调用。

某次采样看到的调用链可能是：

```text
Tomcat 工作线程
  -> OrderController.create()
    -> OrderService.createOrder()
      -> JSON 序列化
```

采集一段时间后，把相同的调用路径合并，统计样本，再生成火焰图。如果大量 CPU 样本落在序列化路径上，这条路径就可能很宽。

原始数据来自运行中的 JVM、线程调用栈及相应性能事件，通常不需要给业务代码补充耗时日志。不同模式的采集机制有所不同，对象分配、锁竞争等还会围绕相应事件记录数据。

注意：采样并不精确记录每次方法调用，因此不能直接从普通 CPU 火焰图得到方法调用次数或单次调用耗时。

## 3. 作用与采样类型

目的：减少性能排查中的盲目猜测，找到值得优化的地方。

| 遇到的现象 | 采样类型 | 用白话解释在看什么 |
|---|---|---|
| CPU 使用率高 | CPU | 线程主要在忙什么计算 |
| 接口慢，CPU 却不高 | Wall-clock | 线程在执行什么，又在哪里等待 |
| 对象创建多、GC 频繁 | Allocation | 哪些调用路径大量创建对象 |
| 并发增加，吞吐量上不去，怀疑锁竞争 | Lock，结合 CPU、wall | 哪些调用路径在竞争、等待锁 |

使用前先确认统计单位和范围：

- CPU 图通常根据 CPU 样本估计开销分布。
- Wall-clock 图包含运行、阻塞和睡眠等状态，需要结合线程及业务路径判断。
- 分配图用来定位分配压力，不等于存活对象分布，也不能直接证明内存泄漏。
- 锁图用于分析竞争和等待，不等于持锁代码自身的 CPU 开销。
- 具体宽度可能按样本数、分配字节或等待时长聚合，取决于工具和输出设置。

## 4. 如何采集

### 4.1 常用工具

| 工具 | 职责 |
|---|---|
| async-profiler | 采集 Java 性能数据，并可直接生成 HTML 火焰图 |
| Arthas profiler | 在 Arthas 中使用 async-profiler 采集和导出结果 |
| JFR 与 JMC | JFR 录制性能事件，JMC 分析录制文件；兼容工具可将相关栈数据转换成火焰图 |

JFR 文件是性能录制文件，本身不是一张火焰图。

### 4.2 使用 Arthas

先连接到目标 Java 进程，再在 Arthas 命令行中执行：

```text
profiler start --event cpu --duration 30 --file /tmp/cpu.html
```

采集 30 秒后自动结束，用浏览器打开生成的 HTML。

如果主要怀疑线程等待，可以在前一次采集结束后，另采一份 wall 图：

```text
profiler start --event wall --threads --duration 30 --file /tmp/wall.html
```

采集应覆盖问题发生的时段，并且有相关业务流量。30 秒可作为初次采集窗口，但是否够用取决于是否覆盖现场。采样仍有开销，应根据应用负载选择时长和事件。

### 4.3 直接使用 async-profiler

安装完成后，在能访问目标 JVM 的环境执行。以下 `12345` 是示例 PID：

```bash
asprof -e cpu -d 30 -f cpu.html 12345
```

### 4.4 在 K8s 中使用

```text
确定问题 Pod
  -> 选中 Java 应用容器
  -> 连接其中的 JVM
  -> 采集并生成 HTML
  -> 导出到本地分析
```

假设命名空间是 `order`，Pod 是 `order-service-abc123`，应用容器是 `app`，容器已经准备好 Arthas，且启动包能够取得所需组件：

```bash
kubectl exec -it -n order order-service-abc123 -c app -- \
  java -jar /opt/arthas/arthas-boot.jar
```

选择目标 Java 进程后，执行前面的 `profiler` 命令。采集完成后，在本地终端导出：

```bash
kubectl cp -n order -c app \
  order-service-abc123:/tmp/cpu.html ./cpu.html
```

`kubectl cp` 依赖容器内的 `tar`。如果没有 `tar`，但有 `cat`，可以使用下面的方式，且不要加 `-t`：

```bash
kubectl exec -n order order-service-abc123 -c app -- \
  cat /tmp/cpu.html > ./cpu.html
```

实际排查时还要注意：

- 无外网环境应提前准备完整离线工具包，只有启动包可能仍需要下载组件。
- 容器里的 Java PID 经常是 `1`，但必须实际确认。
- Attach 失败时检查运行用户、JVM 配置及临时目录权限。
- CPU 采样受容器安全策略限制时，检查具体错误；工具支持时可考虑 `ctimer` CPU 采样。换成 wall 后不能继续当作 CPU 图解释。
- 极简镜像可考虑临时调试容器，但进程可见性、挂载命名空间、库路径和权限仍需处理。
- 多副本服务要选中真正发生问题的实例；同时查看 CPU limit 和 throttling，不能只检查业务代码。

## 5. 如何读懂火焰图

以下针对常见的、从下往上展开的 CPU 火焰图。有些工具会倒置显示，但调用关系和宽度的含义不变。

| 图中的部分 | 含义 |
|---|---|
| 一个方块 | 调用栈中的一个方法或函数 |
| 上下关系 | 下方调用上方 |
| 方块宽度 | 包含该调用路径的样本占比 |
| 整体高度 | 调用层数，不代表执行时间长 |
| 左右位置 | 聚合排列位置，不是执行时间顺序 |
| 颜色 | 看工具图例，不能直接认为越红越慢 |

### 5.1 累计开销与自身开销

父方法的宽度包含子调用。最宽的入口方法不一定是需要修改的位置。

假设在一个简化示例中：

- `createOrder()` 累计占全部样本的 80%。
- 它的全部直接子调用合计占全部样本的 70%。
- 那么它自身对应的样本占比约为 10%。

这里所有百分比使用同一个分母。不能把多层子孙方法的累计占比相加，否则会重复计算。

读图时要区分：

- **累计开销（total / inclusive）**：自己以及子调用涉及的样本。
- **自身开销（self）**：落在自己这一层、没有继续落入子调用的样本。

在标准 CPU 火焰图中，较宽、没有被子框覆盖的部分是查看自身热点的线索。也可以直接看工具展示的 self 指标。

### 5.2 什么样的图算正常

没有统一的正常形状，要判断热点是否符合业务预期。

- 框架入口很宽，可能只是因为所有请求都经过它。
- 调用链很高，可能只是框架和业务层数较多。
- JSON 序列化较宽，在大量数据输出的服务中可能符合预期。
- Wall 图里大量 `park`、`wait`，可能是线程池正常等待任务。

如果系统指标符合预期，某个方法很宽也未必是问题。相近负载下与正常时段对比，通常比孤立判断一张图更有价值。

## 6. 如何根据火焰图分析问题

### 第一步：确认类型与范围

先确认采了什么事件、哪个实例、哪些线程、哪个时间段，以及问题是否在采样期间发生。

### 第二步：寻找较宽的调用路径

可以搜索业务包名，沿业务调用深入。同时留意 JVM、GC、原生函数中的热点，不能只盯业务方法。

### 第三步：找到具体执行工作的位置

优先查看自身占比较高的栈帧，再追溯是谁调用它。不要停在 `Thread.run()`、Controller 等宽大的入口上。

Wall 图则要聚焦相关业务线程和路径，区分正常空闲与请求处理中的等待；必要时结合链路追踪确认等待对请求延迟的影响。

### 第四步：回到代码确认原因

需要回答的问题包括：

- 是业务必须做的大量计算，还是循环中的重复处理？
- 是单次操作成本高，还是调用过于频繁？采样占比本身不能区分两者。
- 是否有不必要的对象转换、序列化或日志参数构造？
- 是否存在外部调用、连接池或锁等待？

火焰图给出线索，代码检查、日志、链路和指标用来确认原因。

### 第五步：验证实际收益

在相近请求量、输入规模、资源配置和预热状态下，对比：

- CPU 使用率；
- 吞吐量与错误率；
- P95 / P99 耗时；
- 分配速率、GC 等相关指标；
- 优化前后的同类火焰图。

P99 可以理解为：99% 的请求耗时不超过这个值。

某个方法从 40% 变成 20%，不一定表示其绝对开销减半，也可能是其他工作变多了。因此不能只看相对占比，还要确认业务结果一致、实际指标改善。

## 7. 常见误区与能力边界

| 误区 | 正确理解 |
|---|---|
| 方法很宽就一定是问题 | 也可能是正常的高频调用或必要计算 |
| 图越高就越慢 | 高度表示调用深度 |
| 从左到右就是执行顺序 | 普通聚合火焰图不按时间排列 |
| 样本占比 60% 就是机器 CPU 使用率 60% | 一个是采样分布，一个是资源利用率 |
| CPU 图能解释所有接口慢 | 等待问题还要看 wall、链路和线程等数据 |
| 分配很多就证明内存泄漏 | 泄漏还要分析对象存活、GC 后基线及引用关系 |
| 图变窄就证明优化成功 | 还要对比绝对指标和业务正确性 |
| 一张聚合图能还原某一次请求 | 普通聚合图通常无法直接还原单次请求，需要链路追踪等配合 |

## 8. 面试讲解与追问

### 8.1 开场讲法

> 我把火焰图理解为程序运行时的开销分布图。它把一段时间内采集到的调用栈聚合起来，帮助我们定位计算热点、等待路径或对象分配来源。
>
> 使用时，我会先根据监控判断问题类型。CPU 高就先看 CPU 图；接口慢但 CPU 不高，就结合 wall 图和链路追踪分析等待。
>
> 读图时主要看宽度和调用关系，同时区分累计开销与自身开销。找到热点后，再回到代码确认是否存在重复计算或不必要的处理。
>
> 优化完成后，我会在相近负载下对比 CPU、接口耗时、吞吐量和错误率，确认实际收益，而不是只看火焰图某一块变窄。

### 8.2 常见追问

| 追问 | 回答重点 |
|---|---|
| 数据怎么来的？ | 来自运行中的 JVM 调用栈采样或相应性能事件，聚合后展示 |
| 为什么选择 CPU 图？ | 监控显示 CPU 开销明显，先定位计算热点；如果主要是等待，就换相应分析方式 |
| 宽度是不是调用次数？ | 普通 CPU 图的宽度是样本占比，不是精确调用次数 |
| 为什么不只看日志？ | 日志能说明事件和阶段耗时，火焰图能补充内部调用路径的开销分布 |
| 最宽的方法一定要改吗？ | 不一定，需要区分自身与子调用开销，并确认业务是否存在浪费 |
| 怎么证明优化有效？ | 控制负载、输入及资源条件，比较实际指标、业务结果和同类火焰图 |

讲自己的项目时，按“业务现象、采集选择、图中发现、代码原因、修改内容、验证结果”组织，使用实际观察到的数据。

## 9. 公开生产案例与完整排查流程

以下是开发者在 HeapDump 社区公开分享的推荐排序服务案例的简化转述，属于线上性能优化，并非事故处置，也不是本知识库维护者的亲历项目。[案例原文](https://heapdump.cn/article/2180390)

### 9.1 发现问题

服务响应偏慢，优化前 P95 耗时约为 110 ms，目标是缩短请求响应时间。

### 9.2 定位慢的阶段

开发者先使用 Arthas `trace`，发现特征获取、预测阶段开销较大，再用 CPU 火焰图检查计算热点。

### 9.3 火焰图给出线索

两条值得检查的路径分别与日志参数的 `toString()`、大量 JSON 反序列化有关。

### 9.4 代码确认原因

DEBUG 日志即使没有输出，传入日志方法前的 `toString()` 仍然执行。另一处用户特征处理原本每个请求只需计算一次，却随着待预测商品数量重复执行。

### 9.5 优化与结果

优化这两处后，作者报告相关热点的样本占比由约 44% 降至 7%，服务 P95 由约 110 ms 降至 70 ms。这是作者报告的前后对比，不能直接解释为机器 CPU 使用率下降了 37 个百分点。

### 9.6 面试时如何讲清因果关系

```text
响应偏慢
  -> 先找到慢的业务阶段
  -> 火焰图发现日志和 JSON 热点
  -> 代码确认存在多余处理
  -> 减少重复工作
  -> 用响应指标验证效果
```

从这个案例可复用的排查方法是：先缩小业务范围，再定位热点，最后确认为什么会产生这些开销。应用到自己的项目时，应补充同负载验证、正确性校验和发布后观察；这些是验证建议，不是原文已披露的实验细节。
