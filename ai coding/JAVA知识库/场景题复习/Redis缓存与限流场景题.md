# 场景题复习：Redis 缓存、主从同步与限流

> 复习主线：Redis 为什么反复全量同步 → 热点缓存失效怎样保护数据库 → 布隆过滤器怎样处理误判 → 限流算法怎样选择和落地 → Redis 故障时怎样降级。
>
> 面试回答尽量按“现象与目标 → 原因或算法 → 方案 → 边界与监控”的顺序展开。下面的容量数字都是示例，实际值应由压测和业务指标确定。

## 1. Redis 为什么频繁出现全量同步？

主从复制正常情况下优先使用部分重同步。副本断开后，只要主节点仍保留副本缺失的复制数据，便可以补传；否则需要重新传输完整数据集。新副本首次连接通常也会全量同步。[Redis 复制文档](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

| 现象或原因 | 为什么会触发或反复尝试全量同步 | 处理方向 |
| --- | --- | --- |
| 网络抖动、复制链路慢 | 副本断开过久，主节点的复制积压缓冲区已覆盖断线期间的数据 | 排查网络和副本延迟；按写入速率与最长断线时间评估积压缓冲区容量 |
| 复制积压缓冲区太小 | 缺失的复制偏移量不再可用 | 调整复制积压缓冲区，并观察部分同步失败次数 |
| 主节点重启或切主 | 新主节点的复制 ID 与副本记录的不匹配，且无法通过历史 ID 完成部分同步 | 排查频繁重启、故障切换和部署操作 |
| 副本处理能力不足或输出缓冲区超限 | 副本被断开；若重连时缺失数据已被覆盖，就退化成全量同步 | 检查副本 CPU、磁盘、网络和复制输出缓冲区限制 |
| 快照生成或传输失败 | 全量同步未完成，连接恢复后可能再次尝试 | 查看主从日志、快照错误、磁盘空间和 I/O |

排查时结合主从日志、复制状态、积压缓冲区大小、复制偏移量，以及 Redis 统计中的全量同步次数、部分同步成功和失败次数。**不要只看到“全量同步次数上涨”就直接调大缓冲区**：先区分是首次加入副本、正常切主，还是同一副本反复断线。无盘复制可以减轻某些磁盘压力，但不能解决网络和积压缓冲区不足。

**面试一句话**：反复全量同步通常是复制链路反复中断，且重连时无法继续部分同步；先查断线原因和复制积压窗口，再按写入量、断线时长调容量。

## 2. 热点商品缓存突然过期，请求打到数据库怎么办？

这是**缓存击穿**：大量请求同时读取同一个失效的热点 Key。先确认数据库能承受的回源并发，以及业务能容忍多旧的数据，再决定读旧值、等待或拒绝。用户提出的四种办法可这样评价：

| 方案 | 能解决什么 | 关键边界 |
| --- | --- | --- |
| 查询时加锁 | 一个实例内只让一个线程重建缓存 | JVM 锁只约束单实例；多实例需要跨实例协调。拿不到锁的请求可短暂等待、重读缓存或返回降级结果，不应一律通知客户失败 |
| 缓存永久不过期，写入时维护 | 避免定时失效造成的瞬时回源 | 更新链路漏写、缓存淘汰和数据不一致仍可能发生；需要兜底校验与修复 |
| 设在低峰时段过期 | 降低高峰同时回源的概率 | 低峰也会有并发；很多 Key 同时过期还可能形成缓存雪崩，应错开到期时间 |
| 定时提前刷新热点 Key | 适合已知的热点集合，减少请求线程回源 | 热点识别、刷新任务失败和重复刷新都要处理；不要扫描全库 Key |

**推荐组合**：对明确的热点商品使用较长的物理 TTL，缓存值里另存逻辑过期时间。读到逻辑过期时，只允许一个执行者异步刷新，其余请求在允许的数据新鲜度范围内继续读旧值；超出允许范围则等待短时间或降级。首次不存在缓存时，按 Key 合并回源，并在获得重建资格后再查一次缓存。对多个实例可使用分布式锁或统一的刷新任务，但要限制锁等待时间和重建并发。[Redis 缓存模式说明](https://redis.io/docs/latest/develop/use-cases/cache-aside/)

**业务边界**：商品展示信息可以视要求短暂读旧；价格、库存、下单资格等关键决策应在权威数据源再次校验。还要监控热点 Key 命中率、重建次数、回源并发、旧值持续时间和刷新失败。

## 3. 缓存穿透使用布隆过滤器，“误杀”如何解决？

布隆过滤器会有**假阳性**：它判断“可能存在”，实际却不存在，于是请求仍可能到数据库。对于已经正确加入过滤器的元素，正常布隆过滤器不会给出假阴性。因此，把过滤器的“肯定不存在”直接用于拒绝时，所谓误杀通常来自**数据未及时加入、过滤器重建遗漏、版本切换或故障**，不是布隆过滤器本身的假阳性。[Redis Bloom filter 文档](https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/)

处理方式：

1. 新增数据成功后可靠地更新过滤器；失败要重试并补偿。过滤器重建时保持新旧版本平滑切换，并定期与数据库对账。
2. 对“可能存在但数据库查不到”的结果缓存短时空值，减少同一个不存在 ID 的重复回源；数据创建后及时删除空值。
3. 对过滤器异常或尚未同步的新数据设置有限回源通道，并用本地或网关限流保护数据库。业务若允许新数据短暂不可见，也可以直接拒绝，但要明确这个一致性取舍。
4. 参数按预计元素量和目标误判率选择；误判率越低，通常需要更多内存。过滤器、空值缓存和限流要配合使用。

**面试一句话**：布隆过滤器的假阳性只会漏过不存在的数据；真正需要防的误杀是数据尚未进入过滤器造成的假阴性，要靠可靠更新、对账和受控回源兜底。

## 4. 固定窗口、滑动窗口和令牌桶怎样讲清楚？

假设要求每秒最多处理约 100 次请求：

| 算法 | 怎么做 | 优点 | 需要说明的边界 |
| --- | --- | --- | --- |
| 固定窗口 | 每个自然秒一个计数器，超过 100 拒绝 | 简单、省内存 | 前一秒末尾 100 次、后一秒开头 100 次，可以在极短时间放行 200 次 |
| 滑动窗口日志 | 保留每次请求的时间戳，统计最近连续 1 秒 | 能严格限制任意连续时间段 | 需要保存窗口内请求记录，高流量时内存和操作成本较高 |
| 滑动窗口计数 | 将时间分成小格，汇总或加权最近的小格 | 比逐条日志省空间 | 是近似值，精度取决于格子大小或加权方法 |
| 令牌桶 | 以固定速率补令牌，桶最多存 100 个；请求消耗令牌 | 允许可控突发，也限制长期平均速率 | 初始满桶时可以短时突发；不保证“任意连续 1 秒严格不超过 100 次” |

选择时先问清需求：要**严格的滚动窗口配额**，选滑动窗口日志；要**平滑长期流量并允许突发**，选令牌桶；规则简单且容忍边界突发，固定窗口即可。[Redis 限流教程](https://redis.io/tutorials/howtos/ratelimiting/)

## 5. Redis Lua 怎样实现令牌桶？

这次讨论的脚本为每个限流 Key 保存两个字段：当前令牌数和上次补充时间。每次请求在一段 Lua 脚本中完成下面的步骤：

1. 校验桶容量和补充速率，从 Redis 的 TIME 获取当前毫秒时间，避免多台应用服务器时钟不一致。
2. 读取状态；第一次请求按满桶初始化。
3. 按经过的时间补充令牌：**新令牌数 = min(桶容量，旧令牌数 + 经过毫秒数 × 每分钟补充数 ÷ 60000)**。
4. 至少有 1 个令牌就扣 1 个并放行；否则拒绝，并计算**需等待毫秒数 = ceil((1 − 当前令牌数) × 60000 ÷ 每分钟补充数)**。
5. 写回令牌数、时间戳，设置空闲过期时间；脚本返回是否放行、剩余完整令牌数和建议等待时间。

Lua 在 Redis 内执行，使单个请求的读取、计算、写入保持原子性。脚本以 Redis 的时间为准，并对时间倒退作保护。空闲过期时间至少覆盖“从空桶补满”的时长，过期后下次请求按满桶初始化；拒绝请求也刷新过期时间，因此持续请求的 Key 会继续占用状态。浮点令牌数用于平滑补充，返回给调用方时可以只显示完整令牌数。[Redis Lua 脚本说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)

**参数怎么定**：每秒补充数要从下游可持续处理能力、服务实例数和预留余量确定；桶容量由可容忍的瞬时并发和突发时长决定。比如下游可稳定承受 10 次/秒、允许短时多放 20 次，可从“每秒 10 个、容量 30 个”开始压测。脚本若接收“每分钟补充数”，应传 600，而不是 10。别把容量误当成每秒限额。

## 6. 接口级和用户级限流如何一起做？

接口级限流保护整个接口及其下游，例如“搜索接口总量每秒 1000”；用户级限流约束单个账号，例如“每人每秒 10”。两者要同时满足，请求才放行。网关或服务入口先识别接口与用户，再使用两个独立维度的桶。

如果先扣接口桶、再扣用户桶，第二步失败时会白白占用第一个桶的令牌。需要严格计数时，在同一 Lua 脚本中**先计算两个桶能否通过，全部通过后再一起扣减**。Redis Cluster 中多 Key 脚本要求这些 Key 位于同一哈希槽，可使用相同的哈希标签；但将一个热门接口的所有用户 Key 放到同一槽也可能使该槽成为热点，需结合分片需求决定是否采用精确的原子双桶方案。[Redis Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)

客户端标识应来自可信的登录态或网关解析结果，不能直接相信用户自报的 ID 或任意请求头。未登录请求可按可信来源 IP、设备或其他标识限流，并考虑共享 IP 带来的误伤。

## 7. Redis 挂了，限流怎么办？

先按接口风险定义降级策略，而不是所有接口统一放行或统一拒绝：

| 场景 | Redis 故障时建议 | 代价 |
| --- | --- | --- |
| 普通查询、体验优先 | 短超时后转为单实例本地限流，必要时保守放行 | 无法维持精确的全局或用户额度 |
| 登录、验证码、支付、成本敏感接口 | 采用更保守的本地限额，无法控制风险时拒绝或返回稍后重试 | 可能影响正常用户 |

本地备用限流器可按实例数分配预算，例如全局每秒 1000 次、10 个实例时先给每实例约 100 次/秒，再留余量并观察偏斜。它无法保证用户在多个实例间的严格总额度。应用应对 Redis 调用设置短超时和熔断，避免每次请求都等待 Redis 故障超时；同时监控降级次数、拒绝量、接口错误率和 Redis 恢复状态。Redis 高可用部署降低故障概率，但不能代替应用侧降级策略。[Redis Sentinel 文档](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

## 8. Guava RateLimiter 是滑动窗口还是令牌桶？

Guava 的 RateLimiter **不是滑动窗口**。默认实现 SmoothBursty 通过储存空闲时积累的许可，并安排下一次可用时间，表现为一种平滑的令牌桶式限流；SmoothWarmingUp 则让许可发放速率逐步升高。它是应用进程内的限流器，不会自动在多个实例间共享额度。[Guava RateLimiter 源码](https://github.com/google/guava/blob/master/guava/src/com/google/common/util/concurrent/RateLimiter.java)、[SmoothRateLimiter 源码](https://github.com/google/guava/blob/master/guava/src/com/google/common/util/concurrent/SmoothRateLimiter.java)

面试时可以这样说：**Guava RateLimiter 适合单机限制平均速率并容忍突发；它不能证明任意连续 1 秒内都不超过 N 次。** acquire 会等待获取许可；tryAcquire 可在给定等待时间内尝试。若要分布式统一额度，通常将状态放到 Redis 或由网关统一执行。

## 9. 滑动窗口有哪些现成实现？

| 选项 | 适合场景 | 使用前确认 |
| --- | --- | --- |
| Sentinel 的 QPS 流控 | Java 服务内的本地限流 | 底层使用分桶统计，属于近似滑动窗口；默认不是跨实例精确共享配额。[Sentinel 工作流程](https://github.com/alibaba/Sentinel/wiki/Sentinel%E5%B7%A5%E4%BD%9C%E4%B8%BB%E6%B5%81%E7%A8%8B) |
| Apache ShenYu 限流插件的 slidingWindow | 已使用 ShenYu 网关，希望在网关配置限流 | 核对插件版本、存储方式、集群一致性和性能。[ShenYu 文档](https://shenyu.apache.org/docs/plugin-center/fault-tolerance/rate-limiter-plugin/) |
| Kong Rate Limiting Advanced | 已使用相应 Kong 版本或服务 | 核对授权、策略和存储配置，窗口统计是近似还是严格。[Kong 文档](https://developer.konghq.com/plugins/rate-limiting-advanced/) |
| Redis 有序集合 + Lua | 必须实现“任意连续 60 秒最多 N 次” | 逐条记录请求时间，精确但消耗内存；Redis 提供示例思路，仍需按业务封装与压测。[Redis Java 限流示例](https://redis.io/docs/latest/develop/use-cases/rate-limiter/java-lettuce/) |

如果题目只要求“每秒平均速率”，令牌桶通常更合适；如果明确要求“任意连续 60 秒不超过 100 次”，要说明选**逐请求记录的滑动窗口**，而不是把 Guava RateLimiter 或固定窗口称作严格滑动窗口。

## 10. 一分钟面试回答

> Redis 反复全量同步，我会先查主从日志、断线原因和复制积压缓冲区是否覆盖了断线期间的写入。热点商品缓存失效，我会用逻辑过期、单执行者刷新和有界旧值兜底来控制回源，并对价格、库存做权威校验。缓存穿透用布隆过滤器时，假阳性只会让少量不存在的数据继续回源；过滤器更新遗漏造成的假阴性才可能误拒绝，所以要可靠更新、对账、空值缓存和受控回源。限流先区分严格滚动窗口还是允许突发：前者用滑动窗口日志，后者用令牌桶。接口总量和用户额度要同时检查，Redis 故障时根据接口风险切换到保守的本地限流或拒绝策略。
