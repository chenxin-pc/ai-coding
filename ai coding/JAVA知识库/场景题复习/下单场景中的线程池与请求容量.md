# 场景题复习：下单场景中的线程池与请求容量

> 复习主线：请求怎样进入应用 → 哪个线程处理下单 → 异步任务进入哪个线程池 → 容量如何估算 → 满载后怎样处理。
>
> 本文以普通同步的 Spring MVC、内嵌 Tomcat 和 `ThreadPoolTaskExecutor` 为主要场景。具体默认值应按项目使用的 Spring Boot、Spring Framework、Tomcat 和 JDK 版本核对。

## 1. 先区分三种线程池与三种容量

| 名称 | 职责 | 容易混淆的点 |
| --- | --- | --- |
| Tomcat 请求工作线程 | 执行进入 Spring MVC 的请求 | 它与业务自定义线程池是两套资源 |
| `ThreadPoolTaskExecutor` | 执行显式提交的业务异步任务 | 配置了线程池，不代表下单请求自动使用它 |
| `ForkJoinPool.commonPool()` | 执行未指定 `Executor` 的多数 `CompletableFuture.*Async()` 任务 | 它默认不使用 Tomcat 或自定义线程池 |

一次典型调用是：客户端连接 Tomcat → Tomcat 工作线程执行下单接口 → 接口按需将任务提交到自定义线程池或 `CompletableFuture` → 任务访问数据库、库存等下游 → 返回结果。若下单接口只是把任务提交到另一线程池后立即等待结果，可能增加一次排队，并不能自然提高吞吐量。

还要区分：**同时处理的请求数**、**已建立的连接数**、**每秒完成的请求数（QPS）**。它们不能相加，也不能互相替代。

## 2. `ThreadPoolExecutor` 的七个参数是什么？

| 参数 | 作用 |
| --- | --- |
| `corePoolSize` | 希望保留的核心线程数；默认不会因空闲而回收 |
| `maximumPoolSize` | 池中允许的最大线程数 |
| `keepAliveTime` | 超过核心线程数的空闲线程等待多久后回收 |
| `unit` | 空闲时间的单位 |
| `workQueue` | 等待执行的任务队列 |
| `threadFactory` | 创建线程，可设置名称等属性 |
| `handler` | 线程数与队列达到上限或线程池关闭后的拒绝处理 |

提交任务时通常按以下顺序处理：

1. 工作线程数小于 `corePoolSize`：新建线程执行任务。
2. 已达到核心线程数：尝试入队。
3. 队列已满：继续新建线程，最多到 `maximumPoolSize`。
4. 队列满且线程数已达上限：执行拒绝策略。

因此，**队列容量会影响是否以及何时用到 `maximumPoolSize`**。无界队列通常使最大线程数难以发挥扩容作用。[Java `ThreadPoolExecutor` 文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)

### 核心线程什么时候创建？

默认是**按需创建**：构造线程池时不会立即创建全部核心线程。即使已有线程空闲，只要线程总数还没有达到 `corePoolSize`，新提交的任务仍可能触发创建新的核心线程。可以通过 `prestartCoreThread()` 或 `prestartAllCoreThreads()` 提前启动；`ThreadPoolTaskExecutor` 对应 `setPrestartAllCoreThreads(true)`。默认情况下核心线程不会因空闲超时；启用 `allowCoreThreadTimeOut(true)` 后可以回收。[Java 文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)、[Spring 文档](https://docs.spring.io/spring-framework/docs/6.1.2/javadoc-api/org/springframework/scheduling/concurrent/ThreadPoolTaskExecutor.html)

## 3. ForkJoinPool 与 CompletableFuture 的默认执行器是什么？

| 创建方式 | 默认目标并行度或执行方式 |
| --- | --- |
| `new ForkJoinPool()` | `Runtime.availableProcessors()` |
| `ForkJoinPool.commonPool()` | 常见 OpenJDK 实现通常取 `max(1, 可用处理器数 − 1)`；可被公共池配置覆盖 |
| 未传 `Executor` 的 `CompletableFuture.*Async()` | 通常使用 `commonPool()`；如果其并行度小于 2，则每个异步任务创建新线程 |
| 不带 `Async` 的 `thenApply()` 等 | 可能由完成上一个阶段的线程执行，不保证进入线程池 |

公共池的默认额外备用线程上限为 **256**，用于部分线程阻塞时维持目标并行度；这不是启动时创建的线程数，也不是“最大只能有 256 个线程”。并行度是目标值，不等于每一刻的线程数。[ForkJoinPool 文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/ForkJoinPool.html)、[OpenJDK 实现参考](https://cr.openjdk.org/~jjg/8186466/webrev.00/src/java.base/share/classes/java/util/concurrent/ForkJoinPool.java.html)、[CompletableFuture 文档](https://docs.oracle.com/en/java/javase/24/docs/api/java.base/java/util/concurrent/CompletableFuture.html)

面试回答重点：下单任务若需要隔离资源或控制并发，应为 `*Async` 显式传入合适的 `Executor`，不要以为它自动使用项目里的 `ThreadPoolTaskExecutor`。

## 4. Spring Boot 最多能接收和处理多少请求？

在普通同步 Spring MVC + 默认内嵌 Tomcat 场景下，当前 Spring Boot 参考文档列出的默认值是：

| 配置 | 默认值 | 含义 |
| --- | ---: | --- |
| `server.tomcat.threads.max` | 200 | 最多约 200 个工作线程同时执行同步请求 |
| `server.tomcat.max-connections` | 8192 | Tomcat 可保持的已接入连接上限 |
| `server.tomcat.accept-count` | 100 | 达到连接上限后，操作系统等待接入的连接队列长度；实际值受系统影响 |

**不是最多只能接收 300 个请求，也不是 200 + 8192 = 8392 个连接。** 200 个线程处理的是已接入连接上的请求；8192 是连接容量，其中可包含空闲的 Keep-Alive 连接；100 是更后面的连接接入等待队列。Tomcat 默认采用 NIO 连接器，因此保持一个空闲连接不需要持续占用一个业务工作线程。8192 是 Tomcat 选定的默认配置值，不是根据当前机器 CPU 自动计算的，也不是 QPS 指标。[Spring Boot 配置文档](https://docs.spring.io/spring-boot/appendix/application-properties/)、[Tomcat Connector 文档](https://tomcat.apache.org/tomcat-11.0-doc/config/http.html)

**QPS 由吞吐能力决定。** 例如 200 个同步请求线程，每个请求平均占用线程 0.5 秒，仅从线程数估算是 `200 ÷ 0.5 = 400 请求/秒`；这是理论估算，数据库连接、库存服务、CPU 等可能先成为瓶颈。若使用 WebFlux、Servlet 异步处理或虚拟线程，上述线程数与同时请求数的关系需要重新分析。

## 5. 下单场景如何确定自定义线程池大小？

先说明线程池实际执行什么：是整个下单流程、每单拆出的并行查询，还是下单后的通知。它们的任务量、耗时和可靠性要求不同。

建议按以下顺序估算并验证：

1. **量任务到达率**：看单实例峰值任务数/秒。若每单提交 3 个异步任务，线程池任务数约为订单数的 3 倍。
2. **量任务占用线程的时间**：包括 CPU 执行和等待数据库、网络的时间，结合平均值及 P95/P99 分布观察长尾。
3. **估算并发**：平均在途任务数约为 `任务数/秒 × 平均占用线程秒数`。例如峰值 100 任务/秒、每个任务平均 0.1 秒，平均约需要 10 个并发线程。
4. **核对硬上限**：数据库连接池、库存或支付服务并发限制、HTTP 连接池、CPU 和内存都可能比线程数更早耗尽。
5. **确定排队预算**：队列应能吸收允许范围内的短暂突发，但排队时间不能超过接口剩余的延迟预算；持续到达率高于处理率时，增大队列只会积压。
6. **逐级压测**：观察订单成功率、P95/P99 延迟、任务排队时长、活跃线程数、队列长度、拒绝次数、CPU、数据库连接等待和下游错误率，再调参数。

上例可以从十几个线程的量级作为**压测起点**，不能直接当生产配置。纯 CPU 任务还要根据实际 CPU 消耗和实例可用核数限制线程数。下单主链路如果必须同步返回结果，应先确认拆线程是否真的减少总耗时。[Java 线程池文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)、[AWS 关于队列积压的实践](https://aws.amazon.com/cn/builders-library/avoiding-insurmountable-queue-backlogs/)

## 6. `ThreadPoolTaskExecutor` 的等待队列怎么选？

`ThreadPoolExecutor` 可以接收多种 `BlockingQueue<Runnable>`；`ThreadPoolTaskExecutor` 的常规配置主要通过 `queueCapacity` 在两种队列间选择：

| `queueCapacity` | Spring 创建的队列 | 对扩容的影响 |
| --- | --- | --- |
| 正数 | 有界 `LinkedBlockingQueue` | 核心线程用满后先排队，队列满了才向 `maxPoolSize` 扩容 |
| `0` 或负数 | `SynchronousQueue` | 不保存等待任务；没有空闲线程时直接尝试扩容，达到上限则拒绝 |

`ThreadPoolTaskExecutor` 的 `queueCapacity` 默认是 `Integer.MAX_VALUE`，近似无界，可能持续积压任务。若直接使用 `ThreadPoolExecutor`，普通业务常选有界 `ArrayBlockingQueue` 或指定容量的 `LinkedBlockingQueue`；前者容量固定，后者入队时会创建链表节点。`PriorityBlockingQueue` 通常无界，且任务必须可比较或提供比较器；`DelayQueue` 是延迟任务队列，均不适合作为普通下单任务的直接替代队列。[Spring 文档](https://docs.spring.io/spring-framework/docs/6.1.2/javadoc-api/org/springframework/scheduling/concurrent/ThreadPoolTaskExecutor.html)、[Java 队列文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/package-summary.html)

选择原则：允许短暂等待就使用**容量有限的正数**；不允许等待就使用 `queueCapacity=0` 并准备接受扩容和拒绝。队列容量应根据突发量与允许排队时间压测确定。

## 7. 拒绝策略如何选？

| 策略 | 拒绝后发生什么 | 下单场景判断 |
| --- | --- | --- |
| `AbortPolicy` | 抛异常，由提交方明确处理 | 核心任务优先考虑；不能把“提交失败”当成“下单成功” |
| `CallerRunsPolicy` | 提交方线程直接执行任务，形成反压；线程池关闭时会丢弃 | 若提交方是 Tomcat 线程，会拉长请求耗时，须核对超时预算 |
| `DiscardPolicy` | 静默丢弃新任务 | 只适合允许丢失的任务，不适合订单、扣库存 |
| `DiscardOldestPolicy` | 丢弃队列中最早等待的任务，再重试提交 | 只适合新任务比旧任务更重要的场景，不适合订单 |

Spring `ThreadPoolTaskExecutor` 默认使用 `AbortPolicy`。拒绝不只发生在线程和队列都满时，也可能发生在线程池关闭时。对需要拿到任务结果的调用，静默丢弃还可能造成结果一直不完成。下单关键任务应记录拒绝、明确反馈，并按业务约定重试或转入可靠的持久化流程。**内存线程池队列本身不能保证进程退出后任务仍在。**[Spring 拒绝策略配置](https://docs.spring.io/spring-framework/docs/6.2.9/javadoc-api/org/springframework/scheduling/concurrent/ExecutorConfigurationSupport.html)、[Java 拒绝策略文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/package-summary.html)

## 8. 一分钟面试回答

> 下单请求先由 Tomcat 接收。普通同步 Spring MVC 场景下，一个请求执行时占用一个 Tomcat 工作线程；连接上限、工作线程上限、接入等待队列和 QPS 是不同概念。业务若拆分异步任务，`ThreadPoolTaskExecutor` 是独立线程池；未指定执行器的 `CompletableFuture.*Async()` 通常使用公共 ForkJoinPool。自定义线程池先根据单实例峰值任务量和任务耗时估算并发，再核对数据库及下游容量；用有界队列控制排队时间，用显式拒绝处理保证下单结果可解释，最后以压测的延迟、拒绝率和下游指标校准。
