# 阶段二：索引与执行计划

## 1. 阶段目标

索引是 MySQL 面试权重最高的模块之一。完成本阶段后，应能回答：

```text
索引的数据结构是什么
  -> 一条查询如何通过索引定位记录
  -> 联合索引能够使用到哪些列
  -> 为什么有索引却不一定使用
  -> 如何通过执行计划验证结论
```

## 2. 为什么常用 B+Tree

InnoDB 索引常用 B+Tree，核心原因是它适合磁盘或页式存储中的范围查询和有序访问。

### 2.1 B+Tree 的特点

- 多叉、平衡，树高较低，一次节点访问可以读取大量键。
- 非叶子节点主要保存键和子页指针，可以容纳更多分支。
- 数据或记录定位信息集中在叶子节点。
- 叶子节点按键有序，并通过链表连接，适合范围查询和排序。
- 从根到任意叶子的路径长度一致，访问比较稳定。

### 2.2 为什么不是普通二叉树

二叉树每个节点分支少，数据量大时树会更高。数据库一次随机页访问成本较高，B+Tree 通过高扇出减少访问层数。

### 2.3 为什么不是哈希

哈希适合等值查询，但通常不擅长：

- 范围查询。
- 按索引顺序排序。
- 前缀匹配。
- `MIN`、`MAX` 等有序访问。

### 2.4 B-Tree 与 B+Tree

B-Tree 的内部节点也可以保存数据，B+Tree 把数据集中到叶子层，内部节点能保存更多键，树高更低；叶子链表也更适合连续范围扫描。

面试回答：

> B+Tree 高度低，能够减少数据页访问；非叶子节点只保存索引键和指针，扇出更高；叶子节点有序且相连，同时支持等值、范围和排序查询，因此适合数据库索引。

## 3. 聚簇索引与二级索引

### 3.1 聚簇索引

InnoDB 通常使用主键构建聚簇索引，叶子节点保存完整行数据。因此一张表只能按照一种顺序组织完整数据，也就只能有一个聚簇索引。

如果没有显式主键，InnoDB 会寻找合适的非空唯一索引；仍没有时，会生成内部隐藏行标识。生产表应主动设计主键，不要依赖隐藏行为。

### 3.2 二级索引

二级索引叶子节点通常保存：

```text
二级索引列值 + 主键值
```

假设有：

```sql
PRIMARY KEY (id),
KEY idx_user_id (user_id)
```

查询完整订单：

```sql
SELECT *
FROM orders
WHERE user_id = 100;
```

流程大致为：

```text
在 idx_user_id 中找到 user_id = 100
  -> 取得对应主键 id
  -> 根据 id 查询聚簇索引
  -> 返回完整行
```

第二次访问聚簇索引就是回表。

## 4. 覆盖索引

如果查询需要的列都能从某个索引中获得，就不必回表：

```sql
KEY idx_user_status (user_id, status)
```

```sql
SELECT user_id, status
FROM orders
WHERE user_id = 100;
```

执行计划的 `Extra` 中可能出现 `Using index`，表示使用了覆盖索引。

覆盖索引可以减少回表和随机页访问，但不能为了覆盖所有查询无限增加索引列，否则会：

- 增大索引体积。
- 降低缓存命中率。
- 增加写入和维护成本。
- 使页分裂、日志和备份成本上升。

## 5. 联合索引与最左前缀原则

假设存在联合索引：

```sql
KEY idx_abc (a, b, c)
```

B+Tree 中先按 `a` 排序，`a` 相同再按 `b` 排序，`a`、`b` 都相同再按 `c` 排序。

### 5.1 常见查询判断

```sql
WHERE a = 1;
```

可以使用索引的 `a`。

```sql
WHERE a = 1 AND b = 2;
```

可以连续使用 `a, b`。

```sql
WHERE a = 1 AND b = 2 AND c = 3;
```

可以连续使用 `a, b, c`。

```sql
WHERE b = 2;
```

传统最左前缀分析中无法直接利用 `a` 后的整体有序性。MySQL 8 的跳跃扫描等优化可能在特定数据分布下使用索引，所以最终仍要看执行计划，不能把口诀说成绝对结论。

```sql
WHERE a = 1 AND c = 3;
```

通常 `a` 用于确定索引范围，`c` 可能通过索引下推过滤，但不能像连续前缀那样直接缩小由 `a` 确定的扫描区间。

```sql
WHERE a > 1 AND b = 2;
```

`a` 是范围条件。传统规则下，后续列通常不能继续用于构造更精确的索引范围，但 `b` 仍可能参与索引下推。必须区分：

```text
用于确定索引扫描范围
和
在存储引擎层利用索引列过滤
```

### 5.2 联合索引字段顺序

设计时综合考虑：

1. 高频查询的共同前缀。
2. 等值条件和范围条件的组合。
3. 区分度与数据分布。
4. 是否服务 `ORDER BY`、`GROUP BY`。
5. 是否可以合理覆盖查询。
6. 索引宽度和写入成本。

“区分度最高的列永远放最前”不是普遍规则。联合索引首先服务真实查询模式。

## 6. 索引下推

索引下推 ICP 的核心是：把能够利用索引列判断的条件交给存储引擎，在回表前尽量过滤记录。

假设索引：

```sql
KEY idx_name_age (name, age)
```

查询：

```sql
SELECT *
FROM users
WHERE name LIKE '张%' AND age = 30;
```

没有索引下推时，可能根据 `name` 找到候选主键后逐条回表，再判断 `age`。有索引下推时，存储引擎可以先在索引记录上判断 `age`，减少回表次数。

执行计划中可能出现：

```text
Using index condition
```

它与覆盖索引不同：

- 覆盖索引：查询所需列都在索引中，不需要回表。
- 索引下推：在回表前利用索引列过滤，可能仍然需要回表。

## 7. 页分裂与递增主键

InnoDB 按页管理数据。向已满的数据页中间插入记录时，可能需要分裂数据页并移动记录，带来额外 I/O、日志和空间碎片。

递增且较短的主键通常具有这些优势：

- 新记录大体追加到索引尾部，减少随机插入和页分裂。
- 主键比较成本低。
- 所有二级索引都保存主键，短主键能减小二级索引体积。

但不要绝对化：

- 分布式系统可能需要全局 ID。
- 严格连续 ID 可能产生写热点或暴露业务量。
- 可以使用趋势递增的分布式 ID，而不是随意使用很长的随机字符串。

## 8. 常见“索引失效”场景

更准确的说法是“索引可能无法用于快速定位，或者优化器认为使用索引成本更高”。

### 8.1 对索引列进行函数或计算

```sql
WHERE YEAR(create_time) = 2026;
WHERE age + 1 = 20;
```

通常应改写为对原始索引列的范围判断：

```sql
WHERE create_time >= '2026-01-01'
  AND create_time <  '2027-01-01';

WHERE age = 19;
```

MySQL 也支持函数索引等能力，但需要显式设计，不能假设普通索引自动适配任意表达式。

### 8.2 隐式类型转换

如果 `phone` 是字符串：

```sql
WHERE phone = 13800138000;
```

类型转换可能影响索引使用或结果正确性。应写成：

```sql
WHERE phone = '13800138000';
```

### 8.3 前置模糊匹配

```sql
WHERE name LIKE '%张';
```

无法根据开头确定连续索引范围。前缀匹配通常更有利于 B+Tree：

```sql
WHERE name LIKE '张%';
```

任意位置检索通常要考虑全文索引或专门搜索引擎。

### 8.4 OR 条件

```sql
WHERE a = 1 OR b = 2;
```

如果两边缺少合适索引，或者合并索引访问成本过高，可能全表扫描。可能的改写包括合理建立索引或在语义允许时拆成 `UNION ALL`，但必须验证重复数据和实际执行计划。

### 8.5 返回数据过多

即使有索引，如果条件匹配表中大部分记录，二级索引扫描加大量回表可能比顺序全表扫描更贵，优化器可能选择全表扫描。

### 8.6 不连续的联合索引前缀

联合索引中跳过左侧列，通常无法充分利用原有排序；范围条件后的列也未必能继续缩小扫描范围。

### 8.7 不等于与否定条件

`!=`、`NOT IN`、`IS NOT NULL` 并非必然不走索引。是否使用取决于数据分布、选择性、覆盖情况和成本估算。

## 9. EXPLAIN 核心字段

```sql
EXPLAIN SELECT ...;
EXPLAIN ANALYZE SELECT ...;
```

`EXPLAIN` 给出优化器估算的计划；`EXPLAIN ANALYZE` 会实际执行查询并提供真实耗时和行数，生产环境使用前必须评估 SQL 的开销和副作用。

### 9.1 type

常见访问类型由好到差可以粗略理解为：

```text
system / const
  -> eq_ref
  -> ref
  -> range
  -> index
  -> ALL
```

含义：

| 类型 | 含义 |
|---|---|
| `const` | 通过主键或唯一索引等值查询，最多一行 |
| `eq_ref` | 连接中通过主键或唯一键匹配一行 |
| `ref` | 通过非唯一索引等值查找多行 |
| `range` | 索引范围扫描 |
| `index` | 扫描整个索引 |
| `ALL` | 全表扫描 |

不能只看 `type` 下结论。小表全表扫描可能完全合理，覆盖索引的 `index` 也可能比大量回表更好。

### 9.2 possible_keys 与 key

- `possible_keys`：优化器认为可能使用的索引。
- `key`：最终选用的索引。

有候选索引但 `key` 为空，可能是成本估算认为全表扫描更便宜。

### 9.3 key_len

表示计划中使用索引键的最大字节长度，可辅助判断联合索引使用到哪些部分。它受字段类型、字符集、是否允许 `NULL` 等因素影响，不应只靠死记数字判断。

### 9.4 rows 与 filtered

- `rows`：优化器预计需要检查的行数。
- `filtered`：预计通过条件过滤后保留的比例。

二者都是估算。`EXPLAIN ANALYZE` 可以用实际行数检查估算偏差。

### 9.5 Extra

常见值：

| Extra | 含义 |
|---|---|
| `Using index` | 覆盖索引，不必回表读取所需列 |
| `Using index condition` | 使用索引下推过滤 |
| `Using where` | Server 层还需要按条件过滤 |
| `Using filesort` | 需要额外排序过程，不等于一定使用磁盘文件 |
| `Using temporary` | 使用内部临时表处理结果 |

`Using filesort` 和 `Using temporary` 是需要关注的信号，但不是看到就必须优化。应结合数据量、耗时和业务目标判断。

## 10. EXPLAIN 分析流程

```text
确认 SQL 返回结果和数据量
  -> 看表访问顺序
  -> 看 type、key 和实际使用的索引
  -> 看预计与实际扫描行数
  -> 判断是否存在大量回表
  -> 看排序、临时表和过滤发生在哪一层
  -> 修改索引或 SQL
  -> 用相同数据再次测量
```

如果估算行数与实际行数差异很大，要考虑：

- 统计信息过旧。
- 数据分布倾斜。
- 列之间存在相关性。
- 参数值差异很大。

## 11. 高频追问

### 11.1 索引越多越好吗？

不是。索引会占用空间，并增加插入、更新、删除、日志、缓存和维护成本。应为真实高频查询、约束和排序需求建立索引，并定期识别重复或无效索引。

### 11.2 低区分度字段不能建索引吗？

不能绝对化。单独给性别等低区分度字段建立普通二级索引，通常收益有限；但它可能作为联合索引的一部分服务特定查询，或者通过覆盖索引减少回表。最终看查询模式和数据分布。

### 11.3 联合索引和多个单列索引等价吗？

不等价。联合索引具有确定的复合排序，可以直接支持多列过滤、排序和覆盖。多个单列索引即使发生 Index Merge，也不一定有相同效果和成本。

### 11.4 唯一索引一定比普通索引快吗？

唯一索引等值查到一条后能停止继续寻找，但实际差距通常不是选型重点。是否需要保证业务唯一性才是核心。
