# 阶段三：事务、MVCC 与锁

## 1. 阶段目标

这一阶段要建立完整链路：

```text
事务为什么需要隔离
  -> 不同隔离级别解决哪些现象
  -> MVCC 如何让读写并发
  -> 当前读为什么需要加锁
  -> 行锁、间隙锁如何导致阻塞或死锁
```

## 2. ACID

### 2.1 原子性 Atomicity

事务中的操作要么全部成功，要么全部失败。部分执行失败时，可以借助 Undo Log 等机制回滚到事务开始前的状态。

### 2.2 一致性 Consistency

事务执行前后，数据库应从一个符合约束的状态转移到另一个符合约束的状态，例如余额不能无故增加、唯一键不能重复。

一致性不是单个日志独立保证的，它依赖：

- 原子性、隔离性和持久性。
- 主键、唯一键、外键等数据库约束。
- 正确的业务逻辑。

### 2.3 隔离性 Isolation

并发事务之间的中间状态不应随意相互干扰。数据库通过隔离级别、MVCC 和锁在并发性能与一致性之间取舍。

### 2.4 持久性 Durability

事务提交后，即使数据库崩溃，修改也不应丢失。InnoDB 主要通过 Redo Log、刷盘策略和恢复机制实现。

面试回答：

> ACID 分别是原子性、一致性、隔离性和持久性。Undo Log 支撑回滚和原子性，锁与 MVCC 支撑隔离性，Redo Log 支撑崩溃恢复和持久性；一致性是数据库机制、约束和业务逻辑共同达到的最终目标。

## 3. 并发异常

### 3.1 脏读

事务 A 读到了事务 B 尚未提交的数据。如果 B 随后回滚，A 读到的就是从未真正生效的数据。

### 3.2 不可重复读

事务 A 在同一事务内两次读取同一行，事务 B 在中间提交了更新，导致两次结果不同。

### 3.3 幻读

事务 A 按某个范围查询两次，事务 B 在中间插入或删除了符合条件的记录，导致第二次看到的行集合发生变化，像出现了“幻影行”。

不可重复读通常强调同一行内容变化；幻读通常强调符合范围条件的行集合变化。

## 4. 四种隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 特点 |
|---|---:|---:|---:|---|
| Read Uncommitted | 可能 | 可能 | 可能 | 隔离性最低 |
| Read Committed | 避免 | 可能 | 可能 | 每次一致性读通常生成新的 Read View |
| Repeatable Read | 避免 | 避免 | 标准定义仍需讨论；InnoDB 通过 MVCC 和 Next-Key Lock 处理常见场景 | InnoDB 常见默认级别 |
| Serializable | 避免 | 避免 | 避免 | 隔离最强，并发代价高 |

### 4.1 RC 与 RR 的关键区别

在 InnoDB 中可以简化理解为：

- RC：每次一致性读通常创建新的 Read View，因此可能看到其他事务新提交的数据。
- RR：一个事务中的一致性读通常复用首次一致性读建立的 Read View，因此多次快照读保持一致。

需要注意：事务开始不一定立即创建 Read View，通常第一次一致性读时才建立。加锁读属于当前读，不按同样方式读取历史快照。

### 4.2 RR 是否彻底消灭所有幻读？

不能只回答一句“完全解决”或“完全没解决”。应区分：

- 普通快照读：通过 MVCC 的一致性视图，重复读取通常看不到其他事务新提交的行。
- 当前读：通过 Record Lock、Gap Lock、Next-Key Lock 等阻止范围内出现影响当前事务的并发写入。
- 快照读与当前读混用：两者可见性机制不同，结果可能发生变化，需要具体分析 SQL 和时序。

## 5. MVCC 的核心结构

MVCC 是多版本并发控制。目标是让大量普通读不必和写操作相互阻塞。

### 5.1 隐藏字段与版本链

InnoDB 记录中包含事务相关的隐藏信息，可以粗略理解为：

- 最近修改该行的事务 ID。
- 指向旧版本信息的回滚指针。

更新一行时，旧值会通过 Undo Log 等信息形成历史版本链：

```text
当前版本 trx_id=120
  -> 旧版本 trx_id=105
  -> 更旧版本 trx_id=91
```

普通查询根据 Read View 判断哪个版本对当前事务可见。

### 5.2 Read View

Read View 可以理解为创建一致性视图时的事务快照信息，通常包含：

- 当时仍活跃的事务 ID 集合。
- 活跃事务中的最小 ID。
- 下一个尚未分配的事务 ID 边界。
- 创建该视图的事务自身 ID。

可见性判断的核心思想：

```text
版本在视图创建前已经提交 -> 通常可见
版本由视图创建时仍活跃的其他事务产生 -> 不可见
版本来自未来事务 -> 不可见
版本由当前事务自己产生 -> 对自己可见
```

如果当前版本不可见，就沿 Undo 版本链寻找更早且可见的版本。

不要在面试中只背事务 ID 数字比较规则，而不说明 Read View 解决的是“当前事务应该看到哪个历史版本”。

## 6. 快照读与当前读

### 6.1 快照读

普通 `SELECT` 在合适隔离级别下通常是快照读：

```sql
SELECT *
FROM orders
WHERE id = 100;
```

它根据 Read View 和版本链读取可见版本，通常不会为读取到的记录增加排他锁，因此读写可以并发。

### 6.2 当前读

当前读读取最新可用版本，并需要对相关记录或范围加锁，例如：

```sql
SELECT * FROM orders WHERE id = 100 FOR UPDATE;
SELECT * FROM orders WHERE id = 100 FOR SHARE;
UPDATE orders SET status = 'PAID' WHERE id = 100;
DELETE FROM orders WHERE id = 100;
```

面试回答：

> 快照读通过 MVCC 读取符合当前 Read View 的历史版本，普通查询通常不会阻塞写；当前读读取最新版本并对记录或范围加锁，更新、删除和加锁查询都属于当前读。

## 7. 锁的基本类型

### 7.1 共享锁与排他锁

- 共享锁 S：允许其他事务继续获取共享锁，但阻止冲突的排他锁。
- 排他锁 X：阻止其他事务获取冲突的共享锁或排他锁。

### 7.2 意向锁

意向锁是表级标记，用于表明事务准备或已经在表中某些行上持有行级共享锁或排他锁。它帮助数据库快速判断表级锁与行级锁是否冲突，不需要逐行检查。

### 7.3 Record Lock

记录锁锁住索引记录。即使表没有按业务字段建立合适索引，InnoDB 的行锁也建立在索引记录之上。

### 7.4 Gap Lock

间隙锁锁住索引记录之间的区间，主要阻止其他事务在该范围插入新记录。它锁的是“间隙”，不是某条已有记录本身。

### 7.5 Next-Key Lock

Next-Key Lock 可以粗略理解为：

```text
Record Lock + Gap Lock
```

它锁住一个索引记录及其前面的间隙，用于当前读范围查询中控制并发插入，处理幻读。

## 8. 索引如何影响加锁范围

假设执行：

```sql
UPDATE orders
SET status = 'CANCELLED'
WHERE order_no = 'A100';
```

如果 `order_no` 有高效索引，数据库可以迅速定位少量索引记录，加锁范围通常更可控。

如果缺少索引，可能扫描并检查大量记录，导致：

- 更多记录参与加锁或锁判断。
- 锁持有时间更长。
- 并发阻塞和死锁概率上升。

“没有索引时行锁一定升级成表锁”不是准确表述。InnoDB 的锁依然基于索引记录，但全表扫描可能锁住大量记录，业务效果看起来接近锁表。

## 9. SELECT FOR UPDATE 的使用

典型库存逻辑：

```sql
START TRANSACTION;

SELECT stock
FROM products
WHERE id = 100
FOR UPDATE;

UPDATE products
SET stock = stock - 1
WHERE id = 100;

COMMIT;
```

注意事项：

- 必须在有效事务中使用，事务边界要明确。
- 查询条件应有合适索引，避免扩大扫描和锁范围。
- 锁住后不要在事务中执行缓慢 RPC、文件操作或人工交互。
- 仅“先查后改”仍需确保检查和修改处于同一事务。

更简单的库存扣减可以使用条件更新：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 100
  AND stock > 0;
```

应用检查受影响行数：为 1 表示扣减成功，为 0 表示库存不足或记录不存在。

## 10. 死锁

### 10.1 典型过程

```text
事务 A 锁住订单 1
事务 B 锁住订单 2
事务 A 等待订单 2
事务 B 等待订单 1
形成循环等待
```

SQL 时序示例：

```text
事务 A                         事务 B
UPDATE id = 1                  UPDATE id = 2
UPDATE id = 2（等待）          UPDATE id = 1（等待）
```

InnoDB 能检测常见死锁，并回滚其中一个事务作为牺牲者，让另一个继续。

### 10.2 死锁的必要条件

操作系统经典表述包括：

1. 互斥。
2. 请求并保持。
3. 不可剥夺。
4. 循环等待。

数据库实践中最有效的是破坏循环等待，例如统一访问顺序。

### 10.3 降低死锁概率

- 所有业务按固定顺序更新资源。
- 缩短事务，避免事务中调用慢 RPC。
- 为查询条件建立合适索引，减少扫描和加锁范围。
- 一次事务处理的数据量不要过大。
- 避免多个流程以不同顺序操作同一批表或记录。
- 应用对死锁失败进行有限次数、带退避的重试。

### 10.4 排查证据

可以查看：

```sql
SHOW ENGINE INNODB STATUS;
```

并结合 MySQL 的锁等待相关系统表、数据库日志、事务 SQL 和应用链路日志，找出：

- 哪些事务持有什么锁。
- 正在等待什么锁。
- 涉及哪些索引记录或范围。
- 两个事务的 SQL 顺序。

只看被回滚的最后一条 SQL 不一定足够，真正形成死锁的锁可能来自同一事务更早执行的语句。

## 11. 长事务的危害

长事务不仅是“占用连接时间长”，还可能：

- 长时间持有锁，阻塞其他事务。
- 阻止旧 Undo 版本被及时清理，使版本链变长。
- 增加回滚成本。
- 使主从复制、备份和 DDL 操作更复杂。
- 造成连接池占用和业务超时连锁反应。

优化原则：

- 明确事务边界。
- 不在事务中做无关的网络和文件操作。
- 大批量操作合理拆分。
- 监控活跃时间过长的事务。

## 12. 高频追问

### 12.1 为什么普通 SELECT 通常不阻塞 UPDATE？

普通一致性读通过 MVCC 读取对当前事务可见的版本，不需要和写事务争夺相同的排他锁。若使用 `FOR UPDATE`、Serializable 隔离级别或特殊语句，则需要另行分析。

### 12.2 MVCC 是否完全不需要锁？

不是。MVCC 主要服务一致性读；写操作、当前读、唯一性检查和外键检查等仍然需要锁。

### 12.3 行锁是否一定只锁一行？

不是。加锁范围由查询条件、使用的索引、隔离级别、访问路径和数据情况共同决定。范围查询可能产生记录锁、间隙锁或 Next-Key Lock。

### 12.4 RC 一定比 RR 快吗？

隔离更弱不等于所有业务一定更快。RC 可能减少部分间隙锁影响，但还要看读写比例、SQL、冲突模式和一致性要求，必须基于业务测试。
